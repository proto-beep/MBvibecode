# MB x Vibecode: Credits Importer – README

**Version 3.34.2** · 2026-10-28 · file `mb-vibecode-credits-importer.user.js` · [changelog](mb-vibecode-credits-importer-CHANGELOG.md)

> **Created with AI:** this script and its documentation were generated by an AI (Claude, by Anthropic). Review what it stages before you submit, see [Created with AI](#created-with-ai).

A userscript for the MusicBrainz release relationship editor (`/release/<MBID>/edit-relationships`). Until 3.0 it was called “Import Discogs credits”. It reads the credits of the linked Discogs release (or of a Bandcamp album or track, or of a text you paste, see [Sources](#sources-discogs-bandcamp-text)), finds the matching MusicBrainz artists through their Discogs links, and shows everything in an import dashboard where you review and adjust every relationship before it is added to the editor.

**The script never submits anything.** Relationships are only staged in the relationship editor, and MB forms for new artists or works are only prefilled. Reviewing and clicking "Enter edit" is always up to you.

The dashboard is available in English, German, Spanish and French. English is the default. Once after the installation (3.26.0) the page bar asks for the language – **English · Deutsch · Español · Français**, the language of your browser preselected; **OK** keeps it (an update does not ask). Later pick another language in **⚙ Settings → General** (until 3.27.0 also next to the **Import credits …** button, until 3.25 in the dashboard header). The choice is remembered in this browser (see [Settings](#settings); **↺ Reset all settings …** there puts all settings back). Edit notes are always written in English.

**English first** (3.27.1): every text of the script is written in English first; German, Spanish and French follow in a translation round every few versions. Until a text is translated, the dashboard shows it in English – so a new tooltip or message can be English for a while in another language. With 3.34.0 every text is translated again (a translation round of 238 texts).

**The languages file** (3.34.0, milestone "Languages file"; collected item E6, maintainer: "Bei E6 sollen alle Sprachen in einem einzelnen add on File sein. Vielleicht kann E6 ganz ans Ende gepaart mit einem Update der übersetzungen"): the texts in German, Spanish and French are a file of their own next to the script, `mb-vibecode-credits-importer-languages.json` (one text a line, so a pull request with a better translation shows only its lines); English – the base of every text and what shows when a text is missing – stays in the script, which is about 380 KB smaller for it. The userscript manager loads the file with the script (`@resource languages …?v=<version>`), like the [mapping file](#the-mapping-file-3330); if it did not, the script fetches it from GitHub itself and keeps it for this version – with a language other than English chosen it then loads the page once more; only if that fails too, a message **languages file missing** with **Update script** appears and the dashboard speaks English (it works as before otherwise). With English chosen, a missing file is fetched quietly for later. The log names the file at each start. The language question after the installation and ⚙ Settings → General stay as they are.

Optional companion script: **MB x Vibecode: Credits Importer Companion** connects the dashboard with a Discogs tab – or, with Bandcamp as the source, a Bandcamp tab (3.17.0, companion 1.8.0) –, for example the other half of a split view, and jumps to the source of each credit there. The **Navigation** switches in ⚙ Settings → Source pages (until 3.27 also below the **Import credits …** button, until 3.25 in the dashboard header) set whether the tab follows on mouse-over or on click, and switch the status marks and the track highlight on or off. See [its README](mb-vibecode-credits-importer-companion-v1.9.0-README.md).

## Installation

1. Install [Violentmonkey](https://violentmonkey.github.io/) (recommended) or [Tampermonkey](https://www.tampermonkey.net/).
2. Open this URL and your script manager will offer to install the script:
   `https://raw.githubusercontent.com/proto-beep/MBvibecode/main/mb-vibecode-credits-importer.user.js`

<a id="the-mapping-file-3330"></a>**The mapping file (3.33.0):** the data of the mapping rules is a file of its own next to the script, `mb-vibecode-credits-importer-mapping.json` (see [Mapping rules](#mapping-rules)). The script manager loads it together with the script (`@resource mapping …?v=<version>` – again with every update) – nothing to do. If it did not (an older manager, Greasemonkey 4), the script fetches the file from GitHub itself (`@connect raw.githubusercontent.com`; Tampermonkey asks once), keeps it in the browser until the next update and loads the page once more; only if that fails too, a message **Mapping file missing** with **Update script** appears (it opens the URL above, so the manager installs the script with the file). The update to 3.33.0 brings the new permissions `@grant GM_getResourceText`, `@grant GM.getResourceUrl` and `@connect raw.githubusercontent.com`; Tampermonkey shows them once. The file is taken from `main` on GitHub: install a version once it is merged there. From 3.34.0 the **languages file** `mb-vibecode-credits-importer-languages.json` comes the same way (`@resource languages`, no new permission; see “The languages file” at the top).

The script file name has no version number on purpose: your script manager checks this exact URL for updates and installs a new version whenever `@version` in the file is higher. The installed version is shown in the script manager and at the top of this README.

The script asks for one permission: to load pages of **bandcamp.com** (`@grant GM_xmlhttpRequest`, `@connect bandcamp.com`) – only to read Bandcamp albums, see [Sources](#sources-discogs-bandcamp-text). From 3.19.2 also to open tabs (`@grant GM_openInTab`), only for the background tab after an import with Harmony, see [Start from the release editor](#start-from-the-release-editor). It still runs in the page itself (`@sandbox raw`), so its connection to the relationship editor stays as before. Bandcamp pages on their own domain (not `….bandcamp.com`) make Tampermonkey ask once whether the script may load them.

**New names, new files (3.3.1):** the script is now called “MB x Vibecode: Credits Importer” (the companion “… Credits Importer Companion”), and its files are new too: `mb-vibecode-credits-importer.user.js` and `mb-vibecode-credits-importer-companion.user.js`. Install both again from the URLs above, then delete “MB x Vibecode: Import Discogs credits” and “… COMPANION” in your script manager – the old files get no more updates, and the old and the new script must not run side by side. If both run, the new one says so above the import button (from 3.3.2 on) and stays out when the old one started first. With 3.5.0 everything stored is reset once – a fresh start (see below).

After an update, a message above the **Import credits …** button lists the milestones since the version you used before (the table "Milestones" of the [changelog](mb-vibecode-credits-importer-CHANGELOG.md), in the dashboard's language), with a link to the changelog. **×** closes it; it stays closed until the next update with new milestones. This happens only when the update raises the "storage generation" of the script, and the maintainer decides that: **2.11.0** did it once, **2.13.0** once more, and **3.5.0** once more as a fresh start with the new names (whichever version you update from): language, switches, window positions, own mapping rules and switched-off rules, the date and track pools and matrices of all releases, the chosen sources and media are back to their defaults. Until 3.5.0 the safety list of created works was kept; the fresh start of 3.5.0 clears it too (asked for by the maintainer). The companion clears its shared storage and the cover box settings on Discogs at the same time (1.4.2, 1.4.3, 1.7.0). Updates in between do not reset anything.

## Usage

1. Open a release on MusicBrainz and go to "Edit relationships" (or, from 3.23.0, use **Enter edit & import credits** when you add or edit a release, see [Start from the release editor](#start-from-the-release-editor)).
2. Click **Import credits …** below the tabs. The switch **window | in the page** next to it sets whether the dashboard opens as a window over the page (default) or in the page itself, below the button (see [Window or page](#window-or-page)). With the beta "Text from cover art" switched on (3.34.8), **… from cover art** joins it: the text of the cover art first, see [Text from cover art (beta)](#text-from-cover-art-beta).
3. The script loads the linked Discogs release. If none is linked, choose another source in the menu **Source ▾** in the head (a Discogs release URL or ID, a Bandcamp album or track URL, or a pasted text); several linked releases of one source are offered in a dialog (see [Sources](#sources-discogs-bandcamp-text)). On a release with several media it first asks which media to import (see [Media choice](#media-choice)).
4. The dashboard lists every Discogs artist with all of their roles, each row with all the fields described below – or, switched on with the symbol ☰ in the head (3.27.0; 3.27.0 – 3.27.1 at first), **compact**, one line per role (see [Compact view](#compact-view)). Each entry is a card with a coloured bar, a label and a tinted header for its kind – **Artist** blue-grey, **Label** teal, **Place** green, **Area** ochre, other entries (series, events …) grey (purple and orange stand for dates and tracks; from 3.32.4 the colours can be changed or switched off in ⚙ Settings → Appearance); an entry not found in MusicBrainz has a red bar, one whose rows are all skipped a grey one:
   - **Artist match:** marked green when an MB artist with exactly this Discogs link exists. Otherwise paste the URL or MBID of the MB artist, search MB in a new tab ("Search MB"), or create the artist ("Create artist …", see below). If several MB artists share the link, pick one.
   - **Header links:** the link to Discogs is its dark "Discogs" tag with ↗ (3.28.0; before, the tag and the name again – the tooltip names the Discogs name), the link to MusicBrainz a purple "MB" tag, so the two are easy to tell apart. MusicBrainz's disambiguation of the matched entry follows in grey parentheses, for example "MB Jane Doe (bassist, US)".
   - **The spelling of the release in the head** (3.32.2; collected item 100, maintainer: "Der Künstle wird auf dem Release/bei Discogs Marc D. Rusch genannt. Dann soll das auch so im Dashboard stehen. Also "Marc D. Rusch" evtl auch mit Sternchen, so wie discogs das macht und wenn ich mit dem Mauszeiger über den Namen gehe im Dashboard soll der Discogs name des entries angezeigt werden. Der Link daneben soll weiter bleiben."): when Discogs credits the entry with a name variation on this release, its head shows that spelling with an asterisk, as Discogs does – **Marc D. Rusch*** for the Discogs artist "Marc Rusch"; the tooltip of the name says "Discogs: Marc Rusch" (and the other spellings of the release, if there are several – the head shows the most frequent one); the link to Discogs stays. The field "Artist credit for all roles" gets the spelling only when it differs from the MusicBrainz name (as before).
   - **How the entry is credited** (3.28.0): when its rows have a "credited as" – the name as the source spells it on this release, e.g. Discogs' "B. Audio" for Bjørk Audio – a chip at the head says **as “B. Audio”** (with several spellings "(+1)"; the tooltip lists them); from 3.32.2 not for the spelling the head shows already. Without a chip the rows use the MusicBrainz name. In the compact view, the line of a row names its own credit when the entry is credited in more than one way.
   - **Narrow or wide:** the fields of a row rearrange with the width of the dashboard (in its window or in the page): wide (from about 1150 px) everything in one line; narrower, three columns – the role | **MB relationship** above **Attributes and credits** | **Level** above **Date** above **Tracks**; below about 700 px two columns, below about 460 px one. Each field has its caption above it, so there is no table head. Make the window wider or narrower and the rows follow.
   - **Rows as boxes:** each row of an entry is a box with a stripe in the colour of the entry's kind, every second one tinted, so the rows ("Played By", "Recorded By" …) are easy to tell apart; their columns line up.
   - **MB relationship:** the suggested relationship type, freely changeable.
   - **Attributes and credits:** instrument or vocal type (with MB's list as suggestions and a check that the name exists in MB), extra attributes such as additional, guest, solo, co, executive, plus role credit and artist credit (see next step).
   - **Level:** recording, release, work, or skip. "Work" puts the credit on the works of the selected tracks. From 3.29.2 each level has its **colour** – the chosen one filled (recording blue, release green, release group ochre, work violet, skip grey), the others underlined in theirs; the compact line shows its level in the same colour. ⚙ Settings → Appearance switches the colours off (the chosen level dark, as until 3.29.1) or gives each level a colour of your own.
   - **Tracks** (orange): pick individual tracks. Dots mark the tracks Discogs gives for this role.
   - **Status:** how many relationships are new, how many already exist on MB, and what is still missing.
   - **Incomplete rows:** the summary above the footer counts the rows that cannot be added yet ("2 rows incomplete": no MusicBrainz match, no type chosen, an invalid date …). **›** (or a click on the count) jumps to the next one, **‹** to the previous one, with "1/2", "2/2" next to it; the row and what is missing in it (the artist match, the type, the date or the instrument) light up for a moment.
   - **▲ ▼ in the status bar** (bottom of the dashboard) jump to the top and to the bottom of the dashboard – in the window its own scrolling, in the page the page's.
   - **Date:** Begin date and End date as in MusicBrainz, see "Dates" below. A date from the date pool or the date matrix is a compact chip ("Performance 1 · 2001-03-01 – 2001-03-03"); **✎** opens its fields.
   - **Already on MusicBrainz:** rows whose relationships all exist on MusicBrainz already are highlighted in green and set to "Skip". They stay in the list; choosing a level brings them back, and the status then shows how many already exist. Rows that exist only partly get a lighter green; only the missing relationships are added. A legend in the toolbar explains both colors.
   - **Remove row** under each role takes the row out of the dashboard, e.g. a credit you do not want to take over; relationships already staged for it are taken out of the editor at the next "Stage". **undo** in the message brings the row back.
   - Below the artists, the section **Companies, etc.** lists the labels, studios and plants from Discogs, see "Companies, etc." below.
5. **Discogs designations:** the details Discogs gives in square brackets and the way an artist is spelled on the release go straight into two editable fields per row:
   - **Role credit:** prefilled with the bracket details that were not already used for the mapping. For example, "Electric Piano [Fender Rhodes]" becomes the instrument "Rhodes piano" with the role credit "Fender Rhodes". The dropdown offers every Discogs variant, written like the role credit (from 3.34.27; before as written on Discogs), but you can type anything. **Lower case** (3.34.27, rule S052; maintainer: "instrumente und role credits immer kleinschreiben außer bei eigennamen"): role credits and tasks are written in lower case – only the proper names of MusicBrainz's instruments ("Hammond", "Rhodes"), the proper names of the register (table T052: "Buddha", makes such as Fender, Gibson, Moog, Wurlitzer, peoples such as Irish, Tibetan) and models with digits ("TR-808") keep their capitals. From 3.34.28 also the words in the brackets of Discogs ("Guitar [Gretsch Duo Jet]" → Gretsch duo jet; maintainer: "S052b, Discogs-Klammern (S011): klein schreiben"). **Names of several words** (3.35.2; collected item 144, maintainer: ""Gibson Les Paul" in dieser Groß- und Kleinschreibung bitte zu Ausnahmen hinzufügen, das ist ja der korrekte name."): an entry of T052 can have several words ("Gibson Les Paul", "Les Paul"); it keeps its spelling only as a whole – "Guitar [Gibson Les Paul]" → Gibson Les Paul, "Les Paul Junior" → Les Paul junior –, a "les" elsewhere stays small. **What was written small is said** (maintainer: ""Buddha" ist natürlich ein eigenname also großgeschrieben … vielleicht deutlich machen, dass gerade etwas lowercased wurde wenn die rolle oder das instrument nicht bekannt ist"): below the field (and in the compact line) a yellow note "Written small – unknown to MusicBrainz: Duo → duo · keep “Duo” · always write “Duo”". Words written small one after another come as a whole first (3.35.2): "Paul Reed Smith → paul reed smith · keep “Paul Reed Smith” · always write “Paul Reed Smith” · Paul → paul · …". **keep** writes the word as written in this row ("Kept as written: Duo · write small again"); **always** adds it to the proper names of the register (T052, stored with your changes of the register, also in ⚙ Mapping rules) – it keeps its capitals everywhere from then on. The note is shown for words of brackets and of roles or instruments MusicBrainz and the register do not know, not for the words of a known role ("Tour Manager" → tour manager), and not once the role credit was typed by hand. Below the field the dashboard shows where the text will be stored: as a credit on the instrument or vocal attribute, in the "task" attribute (e.g. for producer, mix, engineer), or, if MusicBrainz has no field for it, only in the edit note.
   - **Artist credit:** prefilled with the Discogs artist name variation (ANV). The header of each artist shows the Discogs name and all spellings used on this release; "Set for all" applies one credit to all roles of that artist.
   - The toolbar sets both kinds of credit for all rows to their Discogs values or clears them.
6. **Works matrix** (section "Works matrix"): one row per work (a track with several works, such as a medley, gets several rows), one column per person or publisher with credits on level "Work". Writing credits are shown only here, not in the artist list; the artist list keeps the artist's match and a note.
   - **Columns** come from the Discogs writing credits, from publishers under "Published By", from entries added by hand with a work-level role, and from writers that are only in MusicBrainz (locked, so differences to Discogs are visible). From MusicBrainz the matrix shows writing and lyrics credits (composer, lyricist, writer, librettist), arrangers (arranger, instrument arranger, vocal arranger, orchestrator) and labels (publishers); other relationships of linked works, such as dedications, are left out, except where a column from Discogs or added by hand has that role. The matrix looks like the date matrix: each column head is a card – from 3.32.4 in the colour of its kind, with its tag (**Artist**, **Label** …; collected item 107, maintainer: "die farblogik von artists und labels sollte auch in der work-matrix erhalten bleiben", "ja bitte blasser"), paler for a column only in MusicBrainz, the cells neutral – with the MB match (and disambiguation), the buttons **▾** (menu), **«** (fold) and **✕** (take out), the roles as chips with the number of works, the column date as a small date chip when one is set, and the "credited as" field. **▾** opens the column's menu: the column date (MusicBrainz's fields and "from pool …"), **all works**, and for publishers their evidence and tools (see below); a click anywhere else closes it. The head of the first column, **Track and work**, counts tracks and works and holds the attributes for all works (see below). The header row and the first column stay in place while scrolling.
   - **The first column** is compact: the track (number, title, Discogs position on the right), then one line with the work – "linked" with its MB link, "new work" or "found", or for a track without a work **＋ New work · Search · via form …** and ⓘ (what the search found, with a link to search MusicBrainz yourself) – and below it the work's attributes. A new work shows its work type and lyrics languages in short ("▸ Song · English"); a click opens the two lists.
   - **Take a column out:** **✕** in the column header sets the column's rows to "Skip" (they stay in the list of rows and can be switched back there); the column stays as a folded stub (»), and a click on it brings the rows back. A column "only in MusicBrainz" is only folded. Nothing of this is stored: the next time the dashboard is opened, all columns are back as imported.
   - **Dates** in the column menu and in a cell's ▾ menu use the same MusicBrainz fields as everywhere ("ended", ⇣, the date pool, pasting a date as MusicBrainz shows it), in a compact grid: **BD** (begin date) and **ED** (end date) with year, month and day exactly one above the other.
   - **Add a column:** pick any entry already in the dashboard (artist or label), choose its role (composer, writer, arranger …) and switch on the cells of its works, or use **all works** in the column menu.
   - **Cells** show the roles as chips, like the dates of the date matrix: **green with a lock** – already in MusicBrainz; **solid** – planned; **yellow with a dashed border** – a suggestion (publisher evidence, a person's own works for a person as publisher, "Commissioned By" without tracks; from 3.31.6 the tracks of the Discogs notes are set, with ⓘ): **✓** keeps it, **×** takes it out, otherwise it is staged like the others; **grey dotted** "… waits for a work" – the track has no work yet; an empty cell shows a dotted **+**. Click a cell to switch its roles on or off; **▾** shows all roles for that kind of entry and a date of its own for the cell (as MusicBrainz shows dates, e.g. "on 2015-01-26", or from the date pool; a pool date can also be dragged onto a cell or onto the head of a column, which sets the column date). Relationships already in MusicBrainz are green and locked. **Dates for them:** a date dropped onto a cell (or set with ▾ "own date") is also added to the relationships of the cell that are in MusicBrainz **without any date** – as an edit of the existing relationship, like the role credits below. The cell then shows "⌚ composer 2001-03-01 …" with **×** to take it back; after staging it shows ✓, the editor shows the relationship as changed (yellow), and the edit note says "added dates to … existing relationships without a date". Dates MusicBrainz already has are never changed: a date dropped onto a cell that only holds dated relationships, or onto a cell without a role, is not set, and a message says why. Cells of columns "only in MusicBrainz" take such a date too. **The column date** does the same for the whole column: it goes onto every relationship of the column that MusicBrainz has without a date (a date a cell got itself stays, and so does one already staged; clearing the column date takes back what it planned). Columns "only in MusicBrainz" have a column date for this as well.
   - **Role codes:** the MusicBrainz names by default (composer, lyricist, writer, publishing …); several roles in one cell stand side by side. A list above the matrix switches to the international CISAC codes (C composer, A lyricist/librettist, CA writer, AR arranger, TR translator, E publisher, SE sub-publisher) or to the GEMA codes (K, T, K+T, B, V, SV). The choice is remembered.
   - **Publishers with evidence:** Discogs names publishers only for the whole release, not for single works. The dashboard reads MusicBrainz's **personal publisher** relationships (artist – label) and suggests a publisher only on the works written by an artist it is the personal publisher of: if Discogs credits X as composer of track 3 and the publisher is X's personal publisher, only track 3 is ticked, as a suggestion (yellow, dashed; ✓ keeps it, × takes it out). Hovering a cell shows the reason. Track lists in the Discogs notes come first (see "Track lists in the Discogs notes" below). Every publisher from Discogs stays in the matrix as a column, also without evidence or when it is not in MusicBrainz; its cells are then off and can be ticked by hand (or all at once with "for all works" in the column menu). Cells you ticked or unticked yourself stay as they are, also after "check evidence" (column menu). A personal publisher relationship that ended before or began after the release date is shown as a hint, not ticked. Personal publishers MusicBrainz knows for a writer but Discogs does not name are offered as a column, never ticked automatically. Sub-publishers (SE) are your choice.
   - **Commissioned By** (rule R099, for companies C037) becomes the work relationship **commissioned** ("was commissioned by"), for persons and labels, as a column of the matrix. Without tracks (rule S024) it is a suggestion on every work (yellow, dashed; × takes it out of a work, ✓ keeps it; the rest is staged); with tracks it is set on the works of those tracks. "Funded By" is not linked automatically.
   - **Same-named works:** for every track without a work the dashboard searches the works of the people the source credits for writing that track (people with a MusicBrainz entry: from Bandcamp or a text, once you have assigned the name). When the writers of a track change – a name assigned, a writing role added or moved to the work level – the track is searched again a moment later (the log says so); a new import searches anew. A work is offered only if one of these people is credited on it in MusicBrainz and its title or one of its aliases matches the track title (ignoring case, punctuation and additions like "(Remastered)"; one letter may be missing, added or different, but digits must match, so "Track 10" is not taken for "Track 1"). Works by other people are never offered, and tracks without writing credits get no suggestions, only a link to search MusicBrainz yourself. Publishers are not searched.
   - **Works of the artists:** besides, the tracks without a work are compared with all works of the release's artists (its artist credit), of the writers and of the musicians (instrument, vocal and performer rows) that have a MusicBrainz entry, in this order: the works linked to the artist (any artist–work relationship) and the works of the artist's recordings – so a cover the artist has recorded before is found too. A work whose title or alias matches the track title (as above) is listed under the track with where it comes from ("work of Test Band", "recorded by Bass Man (“Song Three (live)”)"); "Link" links it like a found work. Special purpose artists (Various Artists, [unknown], [traditional] … and any name entirely in square brackets, table T026 in [Mapping rules](#mapping-rules)) are left out – their catalogues say nothing about a release; the log names them once. This runs in the background, one request a second as MusicBrainz asks, while the dashboard's own requests go first; each artist is read once and kept in the browser for 7 days (also beyond reloading the page; a second import compares again without asking MusicBrainz). The limit of 4,000 works and recordings per artist, the message, the days and whether the comparison runs at all are set in **⚙ Settings → Works**, where the stored works can be cleared too. When one artist takes longer than 10 seconds because of a large catalogue, a message says so; at most 4,000 works and recordings are read per artist together (a message says so too). The log names the works read and the result. The matrix is drawn anew only when something was found, and not while you type in one of its fields. Nothing is linked by itself.
   - Before creating a new work the dashboard warns if a same-named work exists (of the writers or of the artists); "Create missing works one by one …" leaves those tracks out.
   - **Work type and lyrics languages:** above the matrix, the defaults for new works; each row without a work can override them. Both lists come from MusicBrainz's own "Add work" form, so they contain every work type and language, named as in your MusicBrainz interface and grouped as there (frequently used first; "[No lyrics]" – MusicBrainz's name for the language code zxx, "no linguistic content" – is always offered first, for instrumental works and works with vocals but no lyrics). A work can have several lyrics languages. Nothing is preselected – except the work type **Song** when Discogs names music and lyrics in one credit ("Music And Lyrics By", rule R098): for all new works when the credit is for the whole release, otherwise for the new works of its tracks (rule S020, marked "S020" next to the list; a type you choose stays).
   - **Attributes of the link between recording and work** (MusicBrainz's "live", "cover", "medley", "partial", "instrumental", "karaoke", "demo", "a cappella" – exactly those MusicBrainz offers for the performance relationship) stand below each work as two-letter short forms: **ac** a cappella · **co** cover · **de** demo · **in** instrumental · **ka** karaoke · **li** live · **me** medley · **pa** partial. A click switches one on or off.
     - **Open or closed:** a work whose link has an attribute – in MusicBrainz, set by hand, preselected, or offered – always shows all of them. A work without any is closed ("none ▸ Attributes"); **▸** opens it for now (not remembered).
     - **Colours:** green and locked – in MusicBrainz already; blue – set; yellow and dashed – offered (see "live"). For a planned link the attributes are staged with it. For a link that already exists in MusicBrainz, an attribute you set is **added to the existing link** (an edit, marked ✎, ✎✓ once staged; the editor shows the link as changed and the edit note says "added attributes (live, cover …) to … existing links").
     - **Head of the first column:** **Attributes for all** – a click sets that attribute for all works (or takes it off when all have it; a half-filled one means "some have it"); **▸ spell out** shows the names instead of the short forms (remembered); **open all rows** opens every work's attributes.

On such a link "live" is only offered as **li?** (yellow, dashed); a click adds it. Hovering says why: for a live recording credit or a track title it names the recording ("Live recording – Discogs credits “Live Recording By” (Name) for this track" – or "for the whole release" when the credit names no tracks), otherwise the live release (release group, format, notes).

Outside a block a line with a rights society after the name counts too. In the Discogs notes the tracks go onto the publisher Discogs lists under "Published By" – also when the notes write the name together or with a number ("FlizmoMusic" = "Flizmo Music", "4WordSeaMusic" = "Fourwordseamusic", rule T046) – **set** (3.31.6; before: suggestions), with ⓘ naming the line of the notes; a publisher Discogs does not list becomes an entry of its own.    - **A publisher with a person's name** (3.31.5, rule S048): a publisher that has no entry of a person in the dashboard but a name like a person's (two to four words with capitals, no word of a company such as "Music", "Publishing", "Songs", no legal form) gets MusicBrainz's **artists** of that name as suggestions first, and **Create artist …**. Chosen as an artist, its publishing is the artist–work "publishing".
   - **On the works or on the release** (3.31.5; collected item 112, maintainer: "bei publishing relationships von Labeln muss auch angeboten werden, dass sie auf release oder work ebene stattfinden können. wir haben ja bereits die möglichkeit in der kompakt info das durchzuklicken. so soll das laufen."): a publisher's row ("Published By") shows in its entry too, on **Works** by default; its level can be changed there like any other row – in the compact view a click on the level goes on to the next one (Works → Skip → Release). For other titles, information in square brackets is left out of the work title ("Song [bonus track]" → work "Song"). Credits on these recordings are not affected.

   - **via form …** is the previous way: it opens MB's "Add work" form inside the dashboard, prefilled with title, work type, lyrics languages and the roles of the row; the work is created as soon as you submit that form, and then linked with the track (staged). **Create missing works one by one via form …** walks through all tracks without a work this way.
   - **Open N works in background tabs** opens every linked or planned work without leaving the page. Background tabs need the companion script (version 0.3.0 or later).

   - **No works and no writing credits yet?** The box above the matrix offers **New works for all N tracks** (created with "Enter edit", like "Batch-add new works"); each row has **＋ New work**. Then add columns as described above.
   - **Scroll bars** (3.30.3; maintainer: "wir brauchen in der work-matrix noch eine leiste um von links nach rechts zu scrollen"): a matrix wider than the dashboard has a scroll bar above it, and – while its lower edge (with its own bar) is out of view – a second one at the bottom of the visible area; all of them move the matrix together.
   - **Fold, skip** (3.18.0): the head **▾ Works matrix** folds and unfolds the matrix (folded, it says how many tracks, works and columns it has; the fold is not remembered). **Skip works** (until 3.32.0 "Skip works matrix"; collected item 106; **Take works again** brings it back) leaves the whole matrix out for this release: nothing of it is staged – no works (also none marked as new), no links to works, no work relationships; its rows (writers, publishers, arrangers …) go to "Skip" and are listed with their entries (from 3.19.3 a setting, ⚙ Settings → Works: "Show the rows skipped with the works matrix with their entries", on; off, the entry only says how many are not shown), and what was staged of it is taken out of the editor with the next staging. The same-named works and the works of the artists are no longer looked up (a lookup running stops). The matrix folds and says "skipped"; you can unfold it to look at it, but not change it, and rows have no "Work" level meanwhile. The choice is remembered for the release (**Delete stored import …** forgets it). **Take works matrix again** brings everything back as it was and the lookups go on.
   - **Many tracks** (3.18.0): from 100 tracks without a work the works section asks before looking up works (on a release with several media already the media choice, 3.20.0), with about how long it takes (MusicBrainz answers one request a second; artists with large catalogues take longer). **Look up works** starts the lookups; **Not now** leaves out only the lookups – the matrix stays and can be used as usual – and **Look up now** starts them later. The number is a setting (⚙ Settings → Works, 0: never ask). Counted are only the tracks without a work, because only they are looked up – the question and the setting say so in a tooltip (3.19.3).

If the form cannot be shown inside the dashboard, "Open in separate window" opens it in a popup window, which works the same way. ## Entries as a matrix (E4)

From 3.34.29 (Block AE, collected items E4, 139, 141; maintainer: "kannst du Block AE umsetzen und als standard führen? die alte darstellung aber als "Legacy" darstellung in den einstellungen behalten") the entries are **a matrix** – the default; **⚙ Settings → Appearance → Entries: Matrix | Legacy** switches (`dci-entries-view`, only "legacy" stored). **Legacy** is the dashboard as before 3.34.29: a row per role, a relationship per instrument. Nothing stored changes when switching, so you can go back at any time; a bookmark branch (`claude/stable-3.34.26`) keeps the code before E4.

It came in steps (3.34.29 – 3.35.0, milestone 3.35.0 "Entries as a matrix"):

- **Joining when staged** (3.34.29): the instruments and voices of an entry go into MusicBrainz as **one relationship per recording** (or release) – same date, artist credit and additional / guest / solo – with all of them, each with its own role credit ("instruments: Go Kurosawa (electric guitar, acoustic guitar, electric bass guitar [electric bass] …)"), as MusicBrainz does in its own dialog. An instrument with its own "solo" is a relationship of its own; an instrument that is there already goes into a second one (MusicBrainz holds an attribute once). Instruments and voices stay apart (two kinds of relationship). **⚙ Settings → Staging → Join the instruments and voices of an entry in one relationship** (on; `dci-join`) – off: a relationship per instrument. A joined relationship that changes after staging (a role credit typed, an instrument added or taken out) is taken out of the editor and staged anew with all its instruments.
- **The entry as a matrix** (3.34.30; mockup version 3): in the full view an entry (a person; from 3.35.5 also companies, places, areas and other entries whose rows offer a date or tracks) shows **blocks** – its instruments together (**"19 instruments → instrument · from 19 rows"**), its voices together, each other role a block of its own ("Mixed By → mix") – and in each block **a line per role** and **a column per event**. An **event** is a level with its tracks and its date – ① Recording · no date · all 8 tracks, ② Recording · 2024-08-14 · tracks 2, 5, ③ Release · no date –, the same events as in the date pool and the date matrix; recordings come first, those with more tracks before an overdub on some. A **line**: the instrument of MusicBrainz (to change; "written “Electric bass”" below when the source wrote it otherwise, red when MusicBrainz does not know it), the **role credit**, **add. · guest · solo** (each instrument on its own), **a tick per event** (a tick is a row of the line in that event: on – the line goes into the event, off – out of it; a role MusicBrainz has not on that level cannot be ticked there), its status ("4 new", "MB artist missing" …), **▸ rows** – the rows of the line with all their fields (type, level, date, tracks …), as before – and **✕** (all its rows out, Skip; the line stays grey, a tick brings it back). The questions of a line ("did you mean chimes …", "Voice", "Written small …") stand below it; an answer is for all its rows. More lines than **⚙ Settings → Staging → Lines of a block shown before “▸ n more”** (8): the others behind **▸ n more: clarinet, marimba …** (lines with a question are always shown).
  **Events shared** by all blocks of an entry up to **⚙ Settings → Staging → Events shared by all roles of an entry up to [3] events**; with more, each block shows only its own (the head says how many), **＋ Event ▾** adds one of the others to the block, and a block folds (▾ / ▸). **One row each** in the head of a block puts each instrument in a block of its own – and a relationship of its own when staged –, **Join in one block** at the foot of the entry joins them again (also when ⚙ Settings → Staging "Join …" is off). The foot counts the relationships the entry stages. The compact view and an entry folded to compact lines keep their lines as before (until 3.35.0).
- **Dates in the matrix** (3.34.31; collected item 139, maintainer: "ja mach das mal", "das soll immer das selbe sein. wenn ich also das event hier editiere verändert sich auch der date/track pool"): the date in the **head of an event** is a field – a date typed there ("2024-08-14", "2024-01 – 2024-07", empty: no date) is the event's: its rows get it as a date of the pool (the pool's date itself changes when they had one – the other rows and work links with it follow); events keep their numbers (without a date before those with one, the earlier first). **A date of the pool dragged** into the matrix (mockup board 4): onto **a line** – its rows, onto **the head of a block** – the rows of all its lines, onto **the head of an event** – the rows in it. A row the date covers (the date has no tracks in the date matrix, or all of the row's) **moves** into the date's event – nothing stays without the date ("ohne und mit Datum auf denselben Tracks: das Instrument wandert"); a message says so, with **↶ Undo**. A row the date covers only in part ("2024-08-14, tracks 2, 5" in the date matrix) stays and gets a row of its own in the date's event (an overdub). With **⇧ Shift** a row stays where it is and gets a row with the date too: a yellow question in its line then – **"electric guitar: all 8 tracks with and without a date – only 2024-03-02 · keep both"** ("only": its tracks without a date go; "keep both": two relationships per recording, one with the date).
- **Compact as a matrix** (3.35.0; mockup board 1, maintainer: "ok ansicht pro event"): in the compact view (☰) – and for an entry folded to compact lines – an entry shows **a line per event** – ① Recording · 2024-01 – 2024-07 · all 8 tracks | electric guitar · acoustic guitar · electric bass guitar “electric bass” … **+ 11 more** · **? Chaims** · **? Voice** –: the matrix turned, each event a line with the roles ticked there as **chips** (their role credit, add. / guest / solo; a question yellow with "?"); the first **⚙ Settings → Staging → Lines of a block shown before “▸ n more”** (8) and "+ n more"; what is missing in red at the end. **A click on a chip** opens the entry's full matrix at its line, **✕** takes the role out of the event (the line "Taken out: …" keeps it), **a chip dragged onto the line of another event** moves the role there (**⇧ Shift**: in both). **by event | by role** at the top right of the entry (per entry, until the next import; the default in **⚙ Settings → Staging → An entry, compact, at first**, `dci-em-by`): by role a line per role with its events. **▸** in the head of the entry shows its full matrix right there, **▾** compact again. After the milestone (Block AH, 3.35.2 – 3.36.0):

- **Lines in another order** (3.35.3; AE-2, maintainer: "bitte noch ziehen ermöglichen", "ja nur bis zum nächsten import"): **⠿** at each line of a block (of more than one line) drags it to another place in its block – dropped on the upper half of another line it goes before it, on the lower half after it (a line above or below shows where); **Alt+↑ / Alt+↓** on ⠿ moves it one place. A level MusicBrainz has not for a row's type keeps the row where it is, and its line says so in yellow: **"Mastered By stays on the level Release: MusicBrainz has no “mastering” on the level Recording · ok"** (maintainer: "ja passt"). MusicBrainz has no relationships on media – a medium is chosen as tracks (the medium's name in the list ticks or unticks all its tracks).
- **Companies and places too** (3.35.5; AE-4, maintainer: "ja können auch in die matrix", "alle einträge die daten und/oder tracks anbieten. solche einträge kommen ja eher selten vor."): a label, a place, an area or another entry is a matrix as well when a row of it offers a date and/or tracks – on recordings ("Recorded At" a place: ① Recording all 8 tracks), or of a type with dates ("Phonographic Copyright (p)" a label: ① Release); each role a block of its own (they have no instruments to join), compact a line per event as for persons. An entry with nothing that offers a date or tracks (publishing on works) keeps its rows.

## Start from the release editor

From 3.19.0 the script also runs on the other pages of a release (`@match …/release/*`); besides the relationship editor it only does this: in the release editor (**Add release** `/release/add`, **Edit release** `/release/<MBID>/edit`), right after **Enter edit** on the tab "Edit note", the button **Enter edit & import credits** (3.23.0; until 3.22 a tick "open relationship editor and start import dashboard"). It looks like MusicBrainz's button, only orange, and is there only when the release has a link to a source the script reads – a **Discogs release, Bandcamp album or Bandcamp track** (from 3.28.1; tab "External links" – saved links and links just entered there). Its first words are MusicBrainz's own ("Enter edit", in MusicBrainz's language), the rest follows the dashboard language ("& Credits importieren"); the tooltip names the links. **Ctrl+Alt+Enter** (Mac: Control+Option+Return) does the same, also from the edit note (on Windows AltGr+Enter too, as AltGr is Ctrl+Alt there). The button can be switched off in ⚙ Settings → Sources (**Release editor: the button “Enter edit & import credits” …**, on; `dci-after-edit-btn`); "Enter edit" itself is never changed.

The button submits like "Enter edit" and then goes on by itself: MusicBrainz shows the release page as always, the script goes on to **Edit relationships** of the release, the dashboard opens and loads the credits. Links entered in the release editor are handed over, so a link MusicBrainz does not have yet (for example while the edit is open for voting) is loaded too: a single such new link is loaded at once, otherwise the dashboard chooses as always (see [Sources](#sources-discogs-bandcamp-text)). The log says that it was started from the release editor.

This only happens in the same tab, right after "Enter edit" (within 10 minutes; a new release only when its page comes from "Add release"); a release page opened in any other way stays as it is. When MusicBrainz reports an error while submitting, nothing is noted.

**Imported with Harmony** (3.19.1): [Harmony](https://harmony.pulsewidth.org.uk/) tells MusicBrainz to go on to its page **Release Actions** after "Enter edit" (Harmony's setting "Redirect to Release Actions after import", on by default). In such a release editor there is no button but a note: "for the Credits Importer: after “Enter edit”, use “Edit relationships with Credits Importer” on Harmony" (3.19.2). **Background tab** (3.19.2): with the setting **Imported with Harmony (Bandcamp, Discogs): open it in a background tab** (⚙ Settings → Sources, on by default) the button is there for releases with a Bandcamp album or Discogs release among their links (its tooltip names the background tab). With it, MusicBrainz goes on to Harmony as usual, and Harmony's page opens "Edit relationships" with the dashboard in a background tab (once – a reload does not open it again) and says "– opened in a background tab" next to its link. For this the script asks for one more permission, to open tabs (`@grant GM_openInTab`). Releases from Spotify, Apple Music, Deezer, Tidal, Qobuz and the like have no credits and get no button. On Harmony's Release Actions the script adds, right below **Add cover art**, the action **Edit relationships with Credits Importer**: it opens "Edit relationships" of the release in a new tab, the dashboard starts by itself and loads the Bandcamp album or Discogs release Harmony looked up – also before MusicBrainz has the link. Harmony's page stays open for its other actions (ISRCs, links, cover art). This works on the official instance `harmony.pulsewidth.org.uk` (`@match …/release/actions*`); there the link is always in English, because the dashboard language of musicbrainz.org cannot be read on another site. Another tool that sends MusicBrainz elsewhere: the note names its address, and the relationship editor does not open by itself.

Such a link can also be made by hand: `https://musicbrainz.org/release/<MBID>/edit-relationships#dci-import&src=<URL of the Discogs release, Bandcamp album or track>` opens the dashboard by itself and loads that source (`src` may be left out or given several times).

## Sources: Discogs, Bandcamp, text

The dashboard reads one source at a time. Each source is read by its own adapter (see [Inside](#inside-sources-and-adapters)); everything else works the same for all of them.

- **Discogs:** the linked Discogs release (as before): credits with their tracks, "Companies, etc.", series, notes. People and companies are found in MusicBrainz through their Discogs links.
- **Bandcamp:** the linked Bandcamp album (a `….bandcamp.com/album/…` link of the MB release, whatever its link type) – from 3.28.1 also a **track page** (`….bandcamp.com/track/…`, a single): its credits, "about" text and its one track are read the same way, once (the setting for the track pages does not read it a second time); a track page that belongs to an album is still read as the release it is linked as. The script reads the album's credits text and its "about" text (the about text only for the recording place and its dates: "recorded at Loft in Cologne, june 16/17 2018" gives the place **Loft** in Cologne with "Recorded At" and the period 2018-06-16 – 2018-06-17 in the date pool, from 3.22.0 "Recorded in Berlin, Germany" the area Berlin (see below); the rest is prose and is left out, and so is a private place such as "recorded at home"; from 3.17.2 also **liner notes**, see below), and – switched on in the **Bandcamp** menu, on by default – the credits of each track page, which then count only for that track (one request per track). The credits text is read like a pasted text (below). The band's own name is linked to its Bandcamp page: it is assigned only when MusicBrainz has an artist with exactly this Bandcamp link **and** the release names that artist exactly as Bandcamp does in its artist credit (the name below the release title; it may differ from the artist's name in MusicBrainz); otherwise it is only a suggestion, which says how the release names it. All other names are found by name, as suggestions.
  - **An album on a label's page** (3.22.1): many labels sell the albums of their artists on their own Bandcamp page ("grabacionesautobombo.bandcamp.com" with an album of Yunclas). When the page's name (Bandcamp's "data-band") is not the album's artist – case, accents and a leading "The" do not count, and "Jane Roe & Friends" on Jane Roe's page is hers –, the page is no link of the artist: it is not looked up and not filled in by **Create artist …**. The artist is searched by name instead, the release's artist of that name first ("release artist"), only as a suggestion. The entry says "The Bandcamp page of this album belongs to Grabaciones Autobombo – not Yunclas's own page …" with a link to the page and, when MusicBrainz has a label with that page, its name ("a label of this release ✓" when it is one); the source line says "on the Bandcamp page of …".
  - **Not found through the link** (3.22.1, also Discogs): a person whose Discogs or Bandcamp link MusicBrainz does not have gets the MusicBrainz entries of the same name as suggestions, the release's artist of that name first – check before assigning.
- **Text:** **Paste text …** opens a field for any credits text – Bandcamp credits copied by hand, a booklet, liner notes, a list of musicians – and one for where it comes from (for the edit note). **Read text** makes it the source. Lines like "Mixed by X", "Mixed and mastered by X", "X – guitar, vocals", "X: guitar, vocals", "Guitar: X, Y", "Artwork: X", "Written by A, mixed by B", "Recorded live at Place, City, date by X", "Mastered by X at Studio", "Tracks 3–5: Strings arranged by X", "Published by X (1, 3)", "℗ 2019 Label" become rows; roles are mapped through the [mapping rules](#mapping-rules), instruments through MusicBrainz's list.
  - **Shared instrument words:** "tenor & soprano sax, trumpet and clarinet" → tenor saxophone, soprano saxophone, trumpet, clarinet; "acoustic & electric guitar" → acoustic guitar, electric guitar. Only words that name a kind of the instrument share it (tenor, soprano, alto, baritone, acoustic, electric, fretless, upright …): "bass & electric guitar" stays bass and electric guitar. From 3.29.0 also a list with commas or slashes only – "Tenor, alto, soprano saxophones", "Tenor / alto / soprano saxophones" → tenor, alto and soprano saxophone, each in the singular (rule S040).
  - **The members of the band** (3.30.7; maintainer: ""Vision Fortune are AC Williams, Alex Townend and Andres Ayerbe" soll die drei Künstler als performer setzen"): the release's artist – or "the band", "the trio", "we" – before "are", "is", "consists of", then the names: each a performer on all tracks (as a suggestion; only names written with capitals, so "The band is now a trio" gives nothing). Also from the "about" text of Bandcamp (rule S041, table T043).
  - **Credits in prose** (3.29.0): names with their roles in brackets after "by" – "A chronicle of rabid deeds, dutifully unearthed from accursed crossroads' soil by K.M. (sounds, words) & E. (voice)." → K.M. performer and lyricist, E. vocals; the words before "by" are no role, the words in the brackets are (table T041: sounds → performer – from 3.30.6 asked, see "Sounds" –, words → lyricist, voice → vocals; from 3.29.1 noises → effects credited "noises", electronics → electronic instruments credited "electronics", field recordings → field recordist; or a role the register knows), and every name needs its brackets (S038). Words of prose around a credit are left out (T042): "Cover artwork channeled by Drahmarduk." → artwork credited "cover artwork", "Logo carved by the guided hand of BMS Illustration." → BMS Illustration, design credited "logo".
  - **Joined verbs before "at"** (3.29.0): "Mixed and mastered at TQA.HQ (July 2026)" → TQA.HQ mixed at and mastered at; a date in brackets after the place is no part of its name, the date goes into the pool for Mix and Mastering (S039, D020).
  - **German, Spanish and French instruments and voices** (3.21.2): "Schlagzeug", "Guitarra eléctrica", "contrebasse", "Gesang", "Coros", "chœurs", "Flügel", "batterie" … are read as their English terms and mapped like them – drums (drum set), electric guitar, double bass, vocals, background vocals, grand piano, drums (drum set). A translation gets **no role credit**: MusicBrainz's own name is used ("Batterie" is not credited "drums"). Accents do not count ("Guitarra electrica"). The kind after the instrument is shared as in Spanish and French ("saxo tenor y soprano" → tenor and soprano saxophone), and "y" separates roles and names ("guitarra y voz", "Coros: Lucía y Marta"; "Kevin Y Lee" keeps his initial). "bajo" and "basse" ask like "Bass"; "Alto" alone asks: viola (Spanish, French), alto saxophone or alto vocals. The spellings, each with its language (`Schlagzeug@de`, `batería@es`, `batterie@fr`), are table T034 in [Mapping rules](#mapping-rules); its search field finds a language ("@fr").
  - **Norwegian, Swedish and Danish roles** (3.28.2, all sources): "Miksa av", "Mixad av", "Mixet af", "Produsert av", "Mastering av", "Grafisk utforming", "Innspilt av" … are read as their English roles (mix, producer, mastering, graphic design, recording …) – as the role of a text ("Miksa av: X") and in the brackets of Discogs, where they only name the role in that language ("Mixed By [Miksa Av]", "Graphics [Grafisk Utforming]", "Producer [Produsert Av]"): such a translation gets **no role credit**. Table T039 in [Mapping rules](#mapping-rules), each spelling with its language (`Miksa av@no`, `Mixad av@sv`, `Mixet af@da`; the search field finds "@no").
  - **Artwork tasks joined by "and"** (3.28.2, all sources): "Artwork [Logo Og Kunst]" (Norwegian: logo and art), "Logo og kunst: X", "Logo and Art" become one row per task – design credited "logo" and artwork credited "art"; each row says the role as written at the source. Only when every part is such a task (table T040: logo, art, artwork, design, photography, illustration, layout in English, Norwegian, Swedish and Danish). Tasks of the same MusicBrainz type stay one row (3.28.4): "Artwork [Design And Layout]" is design credited "design and layout".
  - **Places with their area:** "Loft, Cologne" and "Loft in Cologne" are the place Loft in the area Cologne; MusicBrainz places of that name are suggested only in that area. What follows "at" without being a place gives no entry: private places ("at home", "at my place") and phrases such as "at the same time", "at last", "at night", "at the end of …", "at first" (word lists T012 and T019 in [Mapping rules](#mapping-rules)); "First Avenue" or "The End Studios" stay places, and so do names in small letters.
  - **A date right after a place** (3.32.5, T047; collected item 117): "All songs recorded and engineered at El Studio in San Francisco on September 3rd and 4th 2016." gives El Studio in the area San Francisco with **recorded at** and **engineered at** (rule C024) on all tracks, the days go into the date pool; "… in September 2016", "… on 2016-09-03" alike. Before, a date in the same part as the place (no comma between them) took the place with it – only the date was found. Also from 3.32.5: an area that begins like a month ("Marseille", "Augsburg", "Decatur") is no month any more and stays the area.
  - **Typos in role words** (3.32.5, rule S050; collected item 115, maintainer: "muisc hat einen schreibfehler", "Wir probieren es mal mit Tippefehler allgemein erkennen"): a part of a text that gives nothing is read once more, with each unknown word of five letters or more that is one letter off a role word (a letter swapped, missing, too many or wrong – the words of T048, and on MusicBrainz those of its relationship types and attributes) read as that word, when the role is known then: "Muisc and cover art by j4vaman" → Music By (composer) and cover art; "Gutiar – Ann Lee" → guitar; "Recordd at Studio X" → recorded at. Only role words are read so, never names. The row says **Read as “Music” (written “Muisc”)** with the rule id; for a role of the works matrix its column head shows **S050** with that text. On by default; off in ⚙ Settings → Texts or in [Mapping rules](#mapping-rules) (takes effect at the next import).
  - **Names** have no links: MusicBrainz entries of that name (or with it as an alias) are shown as **suggestions** (dashed, yellow), as a block right below the red mark of the entry (side by side, in more lines when there are many) – a click assigns one; nothing is assigned by itself. The small **↗** at each suggestion opens its MusicBrainz entry in a new tab, to check it first (3.17.4). Why a suggestion is there is its tooltip; a short mark says what matters ("similar name", "via Discogs alias …", "spelled differently" when found via the Bandcamp link but spelled differently, "release artist" when the text names no one). Five are shown, the rest behind **+ n more**. Accents, case and punctuation do not count ("Agusti Fernández" finds "Agustí Fernández"); a middle name or an initial more or less is shown as **similar name** ("Barry Guy" finds "Barry John Guy"), after the same names – check it before assigning. A name with an initial is also searched with its written-out words, so "T. Snekkestad" finds "Torben Snekkestad" and "Barry J. Guy" "Barry John Guy"; the initials must fit the first and middle names in their order.
  - **Credits in sentences** (rules for any free text – pasted, or Bandcamp's credits): "Music played and recorded by X in September and October 2026." → X: performer and recording engineer; "Mixed and mastered by X in October 2026." → mix and mastering. Words that only say what was done ("Music", "Songs", "The album" before the verb) are not part of the role, and the time after the name is not part of the name – it goes into the date pool ("September and October 2026" is one period, 2026-09 – 2026-10). "Photography Tom Barrett" or "mastering john doe" (a role, then a name, without a separator) are read too, when the line gives nothing else.
  - **"… created by a human":** "Music and artwork of this release were entirely created by a (cat assisted) human." names roles but no one. For "a human", "me", "us", "the band", "the artist", "himself" … the release's artists are offered for these roles, as an entry of its own with a suggestion ("The text names no one here (“a human”) – the release's artist?"); nothing is assigned by itself.
  - **The label line** ("An Echo Elberfeld release.", "Released on X Records") is left out – the label is set in the release editor; ℗ and © lines are credits. The word lists of these rules are T020 – T025 in [Mapping rules](#mapping-rules).
  - **Distribution** (3.17.3): "Distribution - !K7", "Distribution: X", "Distribution by X", "Distributor: X", "Distributed by / through X", "Vertrieb: X", "Distribución: X", "Distribué par X" … give the company with "Distributed By" – a label that distributes the release (MB: distributed). The words are T028.
  - **Several sentences in one line** (3.21.0): "Cover art: … Graphic design: Jonas Schoder. Text: Evan Parker. Produced by Maya Homburger and Barry Guy." is read sentence by sentence. A period after an initial ("J. Smith"), after short words such as "Vol.", "feat.", "St." (T029) or before a small letter ends no sentence; a line is only cut when a later sentence starts a credit ("Role: …", "… by …", ℗ / ©), so prose stays whole.
  - **℗ and ©** (3.21.0): "℗ 2019 Label" and "© 2019 Label" give one role, "P + © 2023 X", "℗ & ©", "(P) & (C)", "℗©" and "©©" both, also with year ranges ("2019–2023"). A code of how it was recorded ("DDD", "ADD"), a catalogue number after "·" or "–", "All rights reserved" and (3.30.9) a year after the name ("© & ℗ TUM Records Oy 2021") are no part of the name (T033). Only the signs named give a role: both for "© & ℗", one for "℗" or "©" alone (maintainer: "nur wenn P und C auch erwähnt sind. falls nur P oder nur C einzeln erwähnt sind soll jeweils nur das angeboten werden"). From 3.30.9 such a line in the **Discogs notes** gives the label too, unless "Companies, etc." lists it with that role (rule S042). A company's name with a legal form is also searched without it (T044): "TUM Records Oy" suggests MusicBrainz's **TUM Records Oy** and **TUM Records** (maintainer: "ICh würde mir wünschen, dass hier beide Labels in der MB Datenbank zur Wahl für P/C angeboten werden").
  - **Publishers** (3.31.0): a heading "Publishers:", "Publishing:" or "[Publishers & Rights Societies]" and the lines below it ("Name-BMI : tracks 1, 6, 8"), a line with a rights society after a name, "Published by X (BMI)" and a line of societies only ("BIEM/GEMA") – see the works matrix (publishers below a heading) and [Companies, etc.](#companies-etc) (rights societies).
  - **Titles in quotation marks, "courtesy of"** (3.21.0): "Cover art: “Madison” 1988 by Albert Irvin, courtesy of the Albert Irvin Estate" gives Albert Irvin for the cover art – the title of the work and its year are no part of the role, and the year is no date of the release (rule D016); "courtesy of …", "by kind permission of …" are no name (T031). A "by" inside a title in quotation marks does not count.
  - **Web addresses** (3.21.0) are never part of a name. A profile right after a name – Instagram, Facebook, X/Twitter, SoundCloud, YouTube, TikTok, Bluesky, Threads, Mixcloud, Vimeo, Myspace, a Bandcamp page – stays with the entry: MusicBrainz is asked for an artist with that link – shown first among the suggestions, marked "via instagram.com", **only a suggestion** –, and **Create artist …** fills it in as the new artist's link. From 3.21.3 the links are shown next to the name (small, grey) only with the setting **Show the web links found next to names in a text at their entries** (⚙ Settings → Sources, off). Artist pages of streaming services (Spotify, Apple Music, Deezer, Tidal, YouTube Music, Qobuz, Amazon Music; 3.21.3) are kept only for **Create artist …** – MusicBrainz is not asked for them. A profile after a label, studio or other company ("℗ 2023 X Records instagram.com/xrecords", "Recorded at Studio Sol instagram.com/studiosol"; 3.21.3) goes to **Create label …** / **Create place …**. Linktree, home pages, e-mail addresses and all other addresses are left out (MusicBrainz does not take Linktree links); a line of only addresses ("www.…", "Contact: …", "Follow us: …") is listed as left out on purpose (T032).
  - **"Logo by X"** (3.21.0) is design with the credit "logo" (rule R101). **"Text: X"** asks: liner notes (an essay in the booklet) or the lyrics (in German "Text" is the lyrics) – nothing is assumed until you choose; "lyricist" moves the row to the works matrix (rule R100, question Q005).
  - **Left out on purpose** (3.21.0): thanks ("Thanks to …", "Special thanks", "Danke", "Gracias", "Merci" …), endorsements ("X plays exclusively on Y bass strings", "uses Z cymbals") and "appears courtesy of …" give no credit; they are listed under "… lines left out on purpose" (T030), apart from the lines not recognized – a credit among them can be added by hand. From 3.21.4 each line says why ("– thanks", "– a maker’s note", "– only web addresses", "– for Vinyl LP – this release: Digital Media").
  - **The medium of the release decides** (3.21.4, for every source): a credit for a medium the MusicBrainz release does not have – "Vinyl LP mastering by X at Y", "Mastered for vinyl by X", "Mastered by X (vinyl)", "Vinyl master: X", "Lacquer cut by X", Discogs "Mastered By [Vinyl]" or "Lacquer Cut By" on a release of Digital Media – gives no row; it is listed as left out on purpose, with the reason, and so is a studio named only for it. "Vinyl LP mastering and digital mastering by X at Y" keeps the digital mastering (and the studio). A medium word that fits the release is no role credit in texts. Only releases whose media all have a known format are checked (rule S026, words T035).
  - **"Translated by X" in Bandcamp credits** (3.21.4) asks: **liner notes** (suggested – it mostly means the translation of the liner notes, with the role credit "translation") or **translator (lyrics)** on the works; nothing is added until you choose (question Q007). In pasted texts and on Discogs it stays translator (R004).
  - **Tracks named by their titles** (3.22.0): "Piano in ‘En Cualquier Lugar Del Mundo' and 'Phenomenology of misery' is a contribution by Juanjo Infraser Haller" gives piano on the two tracks of these titles; "Guitar on “Song”: X", "X – trumpet on 'A' and 'B'" and "Saxophone on 'A' was played by X" too. The quotation marks may be mixed (‘…' and '…'). The titles are looked for among the tracks – of MusicBrainz for a pasted text, of the album for Bandcamp; case, accents and punctuation do not count, and one letter more, less or other is fine ("Song Too" finds "Song Two"). The row names the titles ("Text: “A”, “B”"); a title not found is shown as **Not matched: “…”**, choose its tracks by hand. "is a contribution", "was played", "were performed" before "by" leave the role (S027, T036).
  - **The area where it was recorded** (3.22.0): "Recorded by Yunclas in Xixon, Asturies, Spain in the Spring/Summer, 2017" gives Yunclas (recording engineer) and **Xixon** as an entry of the kind **Area**, with "(Asturies, Spain)" after it and the type **recorded in** on the recordings; "Recorded in Berlin, Germany", "Mixed live in Paris by X" and "Mastered in Frankfurt am Main by X" likewise (recorded in, mixed in – recordings; mastered in – the release; from 3.22.2 also produced in, remixed in, engineered in). MusicBrainz is searched with the other names of an area too – "Xixon" finds **Gijón** by its alias "Xixón" – and the suggestion names its type and the area it is part of ("City, Asturias"); as with names it is **only a suggestion**. Areas cannot be created here (MusicBrainz's area editors add them): pick a suggestion or paste the MBID of the area. An area is words with capitals (particles between them: "Frankfurt am Main", "Rio de Janeiro"), no month or season ("in March 2019", "in the spring" are dates), and not "Dolby Atmos", "Studio …" and the like (T037). An "in …" that is none ("Recorded in the living room by X", "Produced by X in Berlin" – producing has no area type) gives X and lists the rest as not recognized. The season and year go to the date pool (2017).
  - **Instruments and the name they are played by** (3.34.19; collected item 137a, rule S051; Go Kurosawa's "soft shakes" on Bandcamp; maintainer: "die liste an durch absätzen getrennten instrumenten und eine zwischenzeile"): lines that are only instruments or voices – one or several each ("Electric guitar", "Drums", … "Voice"), empty lines between them allowed – followed by a line "are played, mixed and produced by Go Kurosawa" give **a row per instrument** for Go Kurosawa, and "Mixed By" and "Produced By" as rows of their own; "played" gives no row of its own then ("ja passt"). The same with "played by X", "performed by X", "All instruments played by X" or "All of the above performed by X"; in one line ("Electric guitar, drums and piano are played by X") and as "X plays guitar, bass and drums" ("ja okay"). Lines before the first instrument (a heading) are read as usual; without such a line the instruments are not recognized, as before. Words that are no instrument MusicBrainz knows become rows too (3.34.20, below).
  - **Instruments MusicBrainz names otherwise, and words that are none** (3.34.20; collected item 137d): spellings of the word list T001 ("Keyboards" → keyboard, "Bongo" → bongos, "Woodblock" → wood block, "Electric bass" → electric bass guitar, "Drums" → drums (drum set)), credited as written. A word of such a list that is no instrument of MusicBrainz asks in its row (yellow, also in the compact line) – **"“Chaims” is no instrument of MusicBrainz – did you mean: chimes · wind chimes · tubular bells · other instruments “chaims”"**: the instruments of MusicBrainz whose name or other name is one or two letters off, or has a word so ("wind chimes"), five at most; nothing is assumed, until then the row is incomplete. A similar instrument chosen gets no role credit (a typo), "other instruments" the word in lower case (from 3.34.27, rule S052 – a proper name of MusicBrainz's instruments or of the register, T052, keeps its capital; before: as written). With none like it ("Buddha machine") the row is **other instruments credited “Buddha machine”** at once (maintainer: "falls keine ähnlichen vorschläge vorhanden sind, kann "other instruments" mit role credit vergeben werden"). Still a row per instrument (several in one: E4).
    From 3.34.26 (137d (c); maintainer: "also c. sticks-and-stones bspw. könnte auch einfach "other instruments" werden. wir wollen das auf keinen fall verlieren", "behalte das als letzte Antwort bei. auch bei discogs other instruments. aber miscellaneous support auch anbieten", "passt") the question has **miscellaneous support (task “…”)** as its last answer, and it is asked everywhere: in a line "Name – roles" ("Barry Guy – double bass, sticks-and-stones": double bass and other instruments “sticks-and-stones” – when the line has at least as many instruments known as such words; otherwise they stay not recognized as before) and for a role of Discogs that is no instrument of MusicBrainz ("Chaims" – before: miscellaneous support at once). Without "other instruments" in MusicBrainz and without similar ones: miscellaneous support, as before.

### Supplement with a second source

The dashboard imports **one source**. A second one only **supplements** it, and only when you ask for it: **＋ Supplement** in the head (3.26.0; before, the bar was always shown below the source) opens the bar **Supplement with**, which lists the other linked sources ("＋ Bandcamp artist.bandcamp.com/album/name", "＋ Discogs 1234") and "＋ Text …" (a pasted text). Next to them a field takes **any other Discogs release (URL or ID) or Bandcamp album or track URL**, also one the release does not link to; **Supplement** (or Enter) reads it like a linked one. A click reads that source and compares it with the rows of the dashboard, row by row – same entry (the same MusicBrainz entry, else the same name; case, accents and punctuation do not count), same MusicBrainz relationship and instrument or vocal, same tracks:

- **The same:** nothing changes; the row gets the mark of the second source next to its own (e.g. **DG BC**).
- **Only in the second source:** a suggestion in the list **Supplements from …** – a **new role** for an entry of the dashboard, or a **new entry** (with what MusicBrainz has for it: found via its link, or entries of the same name as suggestions; nothing is assigned by itself).
- **Different tracks:** **differs**, with both track lists. Until you choose, the loaded source stays; the row is marked "BC ≠".
- Lines of a text that gave no credit: **not recognized**, to add by hand.

The list has a checkbox per suggestion (new roles and entries are ticked, "differs" is not), **select all**, **Take over selected** and **Discard all**. What you take over goes into the entries with the mark of its source; for "differs" the row takes the tracks of the second source. What you do not take over stays in the list until you discard it. **remove** next to the source ends the supplement (what was taken over stays). One supplement at a time: another one replaces the list; a new import of the main source starts without any. Nothing of a supplement is stored.

### Remember per release (Cache)

From 3.36.0 (milestone; collected item 146, maintainer: "vielleicht können wir global einen schalter einführen, der sich änderungen und import einstellungen an releases merkt oder eben nicht. standardmäßig auf jeden fall aus", "ja genau, soll alles wieder kommen. aber nur wenn man das ausdrücklich in den einstellungen aktiviert hat") the dashboard remembers a release only when you switch it on: **⚙ Settings → Cache → Remember changes and import settings per release** (off by default).

- **Off** (the default): every import starts afresh. Nothing of a release is stored or read again – not its pools and date matrix, not the source or the media chosen for it, not "Skip works", "Leave out the about text" or the credits switched off on the source pages, not the frames of its images (until 3.35 these were always kept). Within the open tab they hold as before (the media choice "remembered" holds until the page is loaded again). What was stored before stays in the browser, unused, until it is forgotten.
- **On**: a release imported again **from the same source** comes back as you left it – all of the above, and (new) **its rows** with what you changed in them (types, levels, role credits, answers, rows taken out or added – a row for another event, a split, a role added by hand –, their order in the matrix), **its entries** (joined or one row each, by event or by role, the MusicBrainz entity chosen by hand, entries added by hand). Stored a second after each change and when the page goes. Switched on, what the tab holds is stored at once.
- **The source changed since** (maintainer, 146d: "ja einverstanden"): what you changed in a row is taken over only while its line at the source is the same; a row whose line is gone or changed comes as the source gives it now, and a yellow message says how many changes were left out ("2 remembered changes no longer fit the source"); new lines of the source come as they are, after the rows of their entry.
- **Not remembered**: what was staged in the relationship editor (it forgets it itself when the page is loaded again), supplements from a second source, the choices of the works matrix (links to works, their attributes), what is open or folded. Rows already in MusicBrainz are skipped anew at each import; "Stage: …" starts with all relationships.
- **Releases to remember: 50** (0 – 100; maintainer: "bitte 1-100. 0=aus"): 0 switches remembering off; switched on with 0, it becomes 50. Beyond the number, the release used longest ago is forgotten first – when something is stored next (3.36.1; not at each step of the field) – and also when the browser's storage for musicbrainz.org (about 5 MB, shared with MusicBrainz itself) is full; then a message says so.
- **Details** (3.36.1): each source of a release keeps its own remembered state (the 3 used last – a pasted text does not replace what was changed in the Discogs import); a row removed with ✕ stays removed; a row already in MusicBrainz taken in again by hand is not skipped anew; with other media chosen than then, the tracks come as the source gives them now; what the mapping rules make of a row is no change of yours. **Switched on in a tab opened while off**, for a release that was remembered before: the tab did not read what is stored, so nothing is written over it – a message offers **Load the page again** to get it back. What is remembered never stops an import: if it cannot be taken over, the log says so and the import is as the source gives it.
- **Forget all remembered releases …** (asks first) forgets every store of every release; beside it the space they take and that of all data of the script in this browser – "12 releases · 1.3 MB · all data of the script in this browser: 2.1 MB" (KB below 1 MB, one decimal, in the number format of the language; maintainer: "lass neben dem rücksetzen button auch den gebrauchten speicher anzeigen in KB oder MB mit einer kommazahl").
- Always kept: the safety list of works created through the dashboard (`dci-created-works:<MBID>`, for the emergency reset) and, with the companion, the status marks on Discogs and Bandcamp.

### Delete stored import

**Delete stored import …** (in the menu **Source ▾**; until 3.25 next to the source) forgets what the script stored for the import of this release – its date pool, track pool and date matrix, the source chosen for it, its media choice, the supplements, its log, (3.36.0) its rows and entries remembered and, with the companion, its status marks – and imports the source anew, as the first time. What is staged in the relationship editor stays (discard it with MusicBrainz's own buttons or by reloading the page), and so does the safety list of created works. It asks first.

**Liner notes in the “about” text** (3.17.2): when the "about" text is prose of at least five sentences (several paragraphs are fine) and a name stands below it – at the end of the last line after a sign ("… our music. — Jane Roe", "~ Jane Roe"), on the line right below, or after an empty line, also with ", place, date" after it ("— Jane Roe, Berlin, May 2019") –, the name gets an entry with the role **Liner Notes** (MusicBrainz: liner notes, on the release). Such texts are mostly written by someone else, so the name is searched in MusicBrainz like any other and only suggested; its row says "From the “about” text". A date by the name goes into the date pool as a suggestion named for it ("Liner notes – Jane Roe"), and from 3.17.6 it also stands in the date cell of the liner notes row as a suggestion (dashed, yellow): **✓** takes it, **✕** leaves it out. The words that make a last line no name ("Special Thanks" …) are table T027 of the register.

**Credits in the “about” text** (3.32.6, rule S049; collected item 115 – Vivarium Recordings, j4vaman "Ephemeral", maintainer: "hier stehen die credits im "falschen" feld ich möchte ermöglichen dass diese auch abgerufen werden", "mach immer lesen bitte. an/ausschaltbar in den einstellungen"): every credit line of the "about" text is read like those of the credits field – "Muisc and cover art by j4vaman" gives j4vaman with composer (the typo read as "Music", rule S050) and cover art –, also when the credits field has credits. Prose gives nothing, and its lines are not listed as not recognized. The rows say "From the “about” text" and go with **Leave out the “about” text**. Before, the "about" text gave only places and areas, the members of the band and the liner notes. On by default; off in ⚙ Settings → Texts ("Bandcamp: read the credits in the “about” text") or in [Mapping rules](#mapping-rules), at the next import. With it (3.32.6, collected item 115b), the **liner notes** may be signed above such credit lines ("-j4vavaman" and below it "Muisc and cover art by j4vaman"), and a signature of one word with small letters or digits counts when it is the name of the album's artist or at most two letters off it ("j4vavaman" for j4vaman, after a sign only). A name at most two letters off a release artist's – of five letters or more – gets that release artist as its first suggestion, marked "similar name" and "release artist"; nothing is assigned.

**Leave out the “about” text** (in the menu **Source ▾**, next to Delete stored import …, for a Bandcamp release with an "about" text): ticked, the places, liner notes and (3.32.6) credits from the "about" text are hidden and its dates leave the date pool and the matrix – at once, without a new import; ticked off again, they are back with what you changed in them. Stored for this release; Delete stored import sets it back.

### Bandcamp view

From 3.17.0 (companion 1.8.0), a Bandcamp tab works like a Discogs tab when Bandcamp is the loaded source – an album page or a track page on `*.bandcamp.com` (pages under a band's own domain are not covered). From 3.28.1 (companion 1.8.4) the loaded source can be a track page itself (a single): a tab on that page is "connected" and has the marks of its credits; a track page of an album belongs to both, the album and itself. The texts of the view then name Bandcamp ("Bandcamp view: connected", "Bandcamp status", "From Bandcamp: …"); the switches are the same.

- **Status marks** only in the credits, **before each part of a line**: "Written by A, mixed by B" gets two marks, "Mixed and mastered by C" two marks side by side (one for each credit). The "about" text gets none. Resting the pointer on a mark shows its row in the dashboard; a click switches the credit (see below).
- **Switch a credit off (3.17.1; from 3.17.5 with a click on the mark itself, before ⊘):** with **Click switches**, a click on a mark switches that credit off – its row goes to **Skip** in the dashboard ("Switched off on Bandcamp"), its mark is greyed and, when all credits of that part are off, the part of the line is greyed and struck through too. Another click switches it on again, with the level it had; so does choosing a level for the row in the dashboard. Each credit of a group ("Mixed and mastered by C") has its own mark. Resting the pointer on a mark shows its row in the dashboard. Kept for the release (also after loading the page again); **Delete stored import** forgets it.
- **Jump to source:** a row marks its part of the line on the album page. A credit of a track page loads that track page and marks it there; its row in the dashboard says "From the track page: 2" with a link. A place from the "about" text marks only its sentence; its row says "From the “about” text". Texts Bandcamp shortened ("more") are opened first.
- **Track highlight** both ways: a track of the works matrix highlights its line in Bandcamp's track list; the pointer on a track there highlights its row in the works matrix.
- **Status on the release page:** as for Discogs, ✓ arrived in MusicBrainz, ✗ staged but not (yet) in MusicBrainz.
- **open in background** and **Load the release there** open or load the Bandcamp album.
- No cover box: Bandcamp only links the front cover.

A credit is found by the text of its line, as the dashboard read it. If the credits on Bandcamp changed since the import, a credit may get no mark; import again. An older companion (before 1.8.0) only connects Discogs: the view then says "needs the companion script 1.8.0 or later".

Userscripts cannot address browser tabs or split views directly. The companion works around this: every Discogs or Bandcamp tab running it announces itself (with its site), and the dashboard sends its commands to one tab of the loaded source's site.

## Names and Discogs aliases

**Apostrophes:** a typewriter apostrophe (') in role credits and artist credits becomes the typographic one (’), from Discogs as well as typed by hand (rule S012).

**Credited as:** for every entry from Discogs that is assigned to a MusicBrainz entry, the name Discogs shows (its name variation, otherwise the Discogs name without its number like "(3)") goes into the "credited as" field whenever it differs from the MusicBrainz name; if both are the same, the field stays empty. This applies to artists as well as studios, labels and the other "Companies, etc." (e.g. Discogs "Power Station" for the MusicBrainz place "Power Station at BerkleeNYC"). Where several MusicBrainz entries carry the Discogs link, the list to choose from stays as before. A "credited as" you typed yourself is never changed. **Only the case differs** (3.28.2): "Voices Of Wonder" on Discogs for the MusicBrainz label Voices of Wonder, a name variation "VALFAR" for Valfar – the field stays empty and MusicBrainz's spelling is used; if you want the other case on purpose, type it in. Then "Artist credit for all roles" stays empty too (3.28.4); a real name variation ("B. Audio") is filled in there as before.

**Credited as from a text or Bandcamp** (3.28.4): a name from a pasted text or from Bandcamp that you link to a MusicBrainz entry (with one of its suggestions or "change") keeps the name as written there in "credited as" – "K.M." for the artist you link it to, "Jane Roe" for Jane A. Roe –, unless it is the same or differs only in its case; placeholders ("the band") and supplements get none. Typed in by hand, it stays.

**Discogs aliases:** Discogs lists pseudonyms as artists of their own ("Aliases"), while MusicBrainz often carries only the Discogs link of the main name. If an artist is not found by its own Discogs link, the dashboard looks at its Discogs aliases and only **suggests** MusicBrainz artists that carry one of their links; nothing is assigned until you click the suggestion. Discogs has no aliases for labels and studios.

## Mapping rules

All rules that turn what a source writes into a MusicBrainz relationship are kept in one register, each with an id: R001 … (roles), W001 … (role credit wordings), Q001 … (questions), S001 … (special handling), C001 … ("Companies, etc."), D001 … (dates) and T001 … (tables and word lists). The same register serves every source – Discogs, Bandcamp and pasted texts: a text is first turned into the notation Discogs uses ("Mixed and mastered by X" → "Mixed By", "Mastered By"), and the register maps it. Since 3.11.0 the register is one section of the script (section 2: role notation, own rules, rule lists, tables and word lists, the functions that apply them, dates); since 3.12.0 the role rules are plain data there – their pattern, types and level, and what goes with them – and only the rules that need code have it. Every id can be found in the script's code: a rule of the register is its own entry, and the places where a special rule or a wording acts carry its id in a comment (e.g. `[S011]`); the overview names the function for each. **Mapping rules** in the dashboard header shows it (including the date rules D001 …) – from 3.30.0 in the dashboard itself, below its head like ⚙ Settings, and never together with them (opening one closes the other; maintainer: "ja standardmäßig im Dashboard und ja soll sich die Einstellung merken. ja nur eines öffnen und das andere schließen"); the symbol opens and closes them. **⧉ As window** in their head puts them into a window of their own (as until 3.29: movable, resizable; ⚙ Settings may be open beside it), **Into the dashboard** in the window back; the choice is remembered (`dci-rules-place`) and also in ⚙ Settings → Appearance ("Mapping rules: in the dashboard | as a window"). **ⓘ and the rule ids at a row** open them as a window (3.30.2, maintainer: "bitte bei Klick auf Regel-ID das Mapping als fenster öffnen standardmäßig aber option in den einstellungen anbieten"), so the row stays in view; ⚙ Settings → Appearance "Rule ids and ⓘ at rows open them: like the symbol" opens them where the symbol does (`dci-rules-rowplace`), and every row shows **ⓘ** with the rules that made it ("ⓘ R033 · W006 · S018") – hover for their notes; **ⓘ** opens the overview with the row's Discogs role in the test field, and **each id** opens it at that rule, highlighted (a search that hid it is cleared): searchable tables of the role rules (ids R001 …, with the MusicBrainz types and the level each one leads to), role credit wordings (W001 …), instrument questions (Q001 …), special handling (S001 …), "Companies, etc." and instrument spellings, **Tables and word lists** (3.33.1: ✎ changes T001, T002, T003, T038, T045 and T048, see below; the others read only: details that tick checkboxes, words that are no role credit, fixed role credits, engineer tasks, the separators, track words, instrument prefixes, private places and company roles of texts, month names and ordinal words, words that name a date group, the date groups, "live" in titles, roles in the notes – T003, T005 … T018), and a field to **try a role** as the source writes it (e.g. "Bass [Upright], Coordinator [Tour]"; with Discogs loaded the window says "Discogs role", otherwise just "role" – the rules are the same): it shows the relationship type, level, instrument, checkboxes, role credit and which rules were applied.

**The mapping file** (3.33.0, milestone "Mapping file"; collected item E7, maintainer: "nimm E7 auf", "Bitte achte darauf dass neue Dateinamen eindeutig dem Script zuzuordnen sind"): the data of the register is in `mb-vibecode-credits-importer-mapping.json` – the role rules R… (their patterns, types, levels, credits; the code of the rules that need it stays in the script), the wordings W…, the questions Q…, the company roles C…, the tables and word lists T… (instruments, words, the patterns of the texts, the rights societies …) and the quick switches with the rules off by default. Regular expressions are written `{"$re": "…", "$flags": "…"}`, sets `{"$set": […]}`. A rule can be changed on GitHub (a pull request) without touching the script's code; the golden tests show which roles change. From 3.33.1 a rule changed with ✎ can be exported as the whole register in the layout of this file – the pull request then shows only its lines. The head of "Mapping rules" says where the data comes from (its version; loaded by the userscript manager, or fetched from GitHub by the script), and the log names it at each start (in orange if its version is not the script's).


**Your own rules** (U001 …) are stored in this browser and tried before the built-in ones:

- **Discogs role → MusicBrainz:** a Discogs role (without details) with its details – either *containing* a text (empty: any details) or *exactly* a text (empty: no details) – becomes the MusicBrainz type and level you choose (also "skip"), optionally with an instrument and a fixed role credit.
- **Discogs spelling → MusicBrainz instrument:** an extra instrument spelling, e.g. "Gtr" → guitar.
- **On/off:** every rule can be switched off, your own ones as well as the built-in ones (R, W, Q, C, S, D). After every change, the dashboard maps its rows again; levels, instruments and credits you set by hand stay. A few rules are **off until switched on** (3.31.7: D023, S046).
- **Quick switches** (3.32.0, milestone; collected item 97d, maintainer: "bitte lass das aber an- und abstellen. im mapping ganz oben evtl. (mit klickbarem verweis dann wo es verwendet wird)"): at the top of "Mapping rules" (in the dashboard and as a window) the rules switched most often, each with its id – a click on the id shows the rule in the lists below, whose note says where it acts. They are the same switches as in the lists: **S045** a rights society after a writer's name → the release's rights society; **D022** Performance on several days → their common month or year; **S021** "live" preselected for live releases; **S031** only the case differs → no "credited as"; **S007** festivals in "Companies, etc." left out – all on by default –; **D023** dates in the titles of the tracks and **S046** "Performer" on tracks → the instruments on those tracks – both off by default. **From 3.32.8** (collected item 116; maintainer: "die quick switches bitte visuell in einem eigenen fenster (rechteck mit oder ohne runde ecken, deine wahl je nach konsistenz). vielleicht alle visuell mit jeweils eigenem button könnte besser sein … als checkboxen") they stand in a box of their own – a framed rectangle with round corners like the other boxes of the dashboard, its head "Quick switches" – in a grid, each switch a **button** with a small slider (on: filled, purple; off: white and grey) and its id attached on the right; a click switches it (before: a line of checkboxes). The name "Quick switches" stays English in every language of the dashboard (3.34.3, maintainer: "Quick Switches bitte nicht übersetzen."); the labels of the switches are translated.
- **✎ Changing built-in rules** (3.33.1; collected item E7, maintainer: "auch direkt an der Regel"): **✎** at a role rule without code (R…), at a company rule (C…) and at the lists T001 (instrument spellings), T002 (words in lower case), T003 (artwork types), T038 (small words of titles), T045 (rights societies) and T048 (role words for typos) opens a form below it. A role rule: its **pattern** – as role words separated by "|" ("photography by | photography | … | pictures by") where it is a plain list of words, otherwise as a regular expression –, its **MusicBrainz types** (several separated by commas, tried in this order), its **level**, its **role credit** (none, as written, or a text) and its **instrument or vocal**; a company rule: its pattern, its types for labels, places, areas and artists, and its level; a list: all its entries, one a line ("BMI = Broadcast Music, Inc. – USA", "gtr = guitar / electric guitar"). Saved, it is **your change**: stored in this browser on top of the mapping file (`dci-mapping-changes`), in effect at once (the rows are mapped again); the rule is marked **changed** (its built-in values in the tooltip). Rules with code (marked **code**) can only be switched on and off. A pattern is checked before it is saved (not empty, at most 400 characters, compiled in the browser); a wrong one is not taken. A change of T045 takes full effect after loading the page again.
- **✎ at wording rules and questions** (3.34.4; collected item 121, maintainer: "bitte gib W und Q auch eine edit funktion", "passt so"): **✎** at every wording rule (W…) – its **words**, one a line, the role with its details in small letters in either order ("upright bass", "bass upright"), and its **role credit** (none or a text) –, at every instrument question (Q001, Q002, Q004) – its **word** ("bass"), the **role credit** it keeps and the **instruments to choose**, one a line in their order – and at every type question (Q003, Q005 …) – its **choices** in a table: type, level, instrument, task, label, role credit (none, as written, a text) and "suggested", with ↑ ↓ to order them, ✕ to remove one and **＋ Add a choice** (at most eight). What asks a type question (its rule, the question's text) stays, code depends on it. A row that answered a type question keeps its answer when the choices change, as long as that choice is still there (otherwise it asks again). Changes of W and Q are exported and imported like the others (also from a whole register); an older script skips them as unknown.
- **Wording rules and questions of your own – ＋ New rule** (3.34.21; collected item 121b, maintainer: "so wie du schreibst"): **＋ New rule** in the heading of the wording rules opens an empty form – the **words** (one a line, "fretless bass", "bass fretless") and the **role credit** they get –, in the heading of the questions one for a question of your own – its **word** ("keys"), the **role credit** it keeps and the **instruments to choose** ("keyboard", "synthesizer", "piano"). Saved, the rule gets an id of its own (W901 …, Q901 … – the built-in rules never take numbers from 900 on), stands first in its table, marked **yours** ("your rule" as its note), and is tried **before the built-in rules**; it is stored with your changes (`dci-mapping-changes`), listed among them as "your rule" with **✕ delete this rule** (asked first), changed with ✎ like the others, switched on and off, and goes with your changes when they are exported and imported (also in the whole register, for a pull request). A word a question of your own asks about is read as a role in texts too ("Key Man – keys") – the row stays an instrument and asks, even when the word is no instrument of MusicBrainz.
- **Your changes of built-in rules** (3.33.1): below your rules, each change with what it changes – for a pattern of role words (3.34.4: and for the words and instruments of W and Q) the words added and taken away ("+ pictures by"), otherwise before → after – and **↺ back to the built-in rule**; **↺ Reset all changes of built-in rules** (both asked first; your own rules and the switches stay). Your changes stay with an update of the script. When an update changed a built-in rule you changed, the rule is marked **changed · ⚠**, the log warns at the start, and the list names the built-in value then and now, with **Keep mine** (the change stays) and **Discard**; a change of a rule that is no longer in the file can only be discarded. The head of "Mapping rules" counts them ("your changes: 2").
- **Export and import** (3.33.1; before: a file `mb-x-vibecode-rules.json` with your rules and switches): **Export** **my changes** – own rules, switches, changed rules and lists, with the script's and the mapping file's versions they were made on – as `mb-vibecode-credits-importer-mapping-changes.json` (small: to keep, move to another browser or share), or **the whole register** with your changes as `mb-vibecode-credits-importer-mapping.json` in the layout of the repository's file (one line per entry – without changes it is the file byte for byte, so a pull request shows only the lines of the changed rules; own rules and switches are not in it); **Save as file** or **Copy** (to the clipboard). **Import** a file (**Import file**, or dropped onto the window) or **pasted text**: a changes file, an old rules file (`mb-x-vibecode-rules`, version 1 – still read) or a whole register (what differs from the mapping file of this version). It is checked first – only data, known ids, only the fields a rule may have, patterns compiled in try/catch, at most 1,000 entries – and nothing is taken over before the **preview**: new, changed and removed rules with their fields before → after and (for patterns of role words) up to three roles mapped before → after, like the test field; lists (+ / −), own rules, switches; **skipped** ids with the reason (not in the mapping file, a rule with code, a list that cannot be changed, a wrong pattern); a **⚠ conflict** when the built-in rule differed at the export. **Merge with my changes** (the default: the file's fields win, the rest stays) or **Replace my changes** (with a whole register: only the changes of built-in rules), then **Take over**. ⚙ Settings → reset with "own mapping rules" ticked resets your changes of built-in rules too.

**Discogs wording is kept.** Where MusicBrainz names an instrument or role differently from Discogs, the Discogs wording is prefilled as role credit, in lower case: "Synth" becomes the instrument synthesizer credited as "synth", "Drums" drums (drum set) credited as "drums", "Backing Vocals" background vocals credited as "backing vocals", "Layout" the relationship design with "layout". Instruments store it as credit; relationship types with a task store it as task; others have no field for it, so it goes into the edit note. Details in brackets that are part of the MB name count as Discogs wording ("Guitar [Electric]" is electric guitar, nothing to credit), and grammatical variants such as "Mixed By" (mix), "Remastered By" (mastering) or "Music By" (composer) are not credited. Other details in brackets always come first: "Drums [Brushes]" is credited as "brushes". **The design of a part of the package** keeps its whole name (3.28.4): "Cover Design", "Design [Cover]", "Cover [Design]", "Artwork [Cover Design]" are design credited "cover design"; the same for sleeve, booklet, package, packaging, digipak, inlay and insert ("Logo Design" stays "logo"). The kind of a voice is credited in lower case (3.28.2): "Vocals [Screams]" → "screams", "Vocals [Clean]" → "clean".

**An instrument by its last word** (3.28.2): when MusicBrainz has no instrument of the whole name (two to four words), the last word is looked for, after every other spelling – first with the words before it ("Soprano Sax" → soprano saxophone), then alone: "wood flutes" is the instrument flute credited as "wood flutes", "Wood Flute" flute credited as "wood flute". In a text, a phrase that looks like a name ("John Bass") is not read this way.

**Lower case and proper names.** Generic words are written in lower case, proper names keep their capitals: "Electric Piano [Fender Rhodes]" links the instrument Rhodes piano credited as "Fender Rhodes", "Synthesizer [Roland Jupiter-8]" is credited as "Roland Jupiter-8". MusicBrainz's own instrument names decide: words written in lower case there are generic, words capitalized there (such as "Rhodes" in "Rhodes piano" or "Hammond" in "Hammond organ") are proper names. Words MusicBrainz does not know, such as brand and model names, are kept as Discogs writes them.

**Every role is kept.** Roles for which MusicBrainz has no specific relationship (for example Management, Stylist, Lighting, Crew) are added as "miscellaneous support" with the Discogs role as task, for example task "Management" or "Management [Tour]". Unknown roles are first checked against MusicBrainz's instruments; if it is no instrument either, the row becomes "miscellaneous support" with the role as task as well. Choose a better type in the row if there is one, or set the row to "Skip".


**Role credit field:** a role credit taken from Discogs is marked with a "from Discogs" tag and a yellow field. The field is offered only where MusicBrainz can store a role credit: on instruments and vocals ("credited as") and in text attributes such as the task of "miscellaneous support" or a series number. Types like mastering, design or liner notes have no such field, so the dashboard does not offer one; the Discogs role stays visible above, and its wording is still documented in the edit note. A trailing "by" is never taken over ("Photography By" → photography), and role credits never contain Discogs brackets: details come before the role ("Coordinator [Tour]" → "tour coordinator"). Role credits of artwork relationships (artwork, art direction, design, design/illustration, graphic design, illustration, photography) are written entirely in lower case.

**"Text By"** becomes liner notes. **Phonographic copyright (℗)** goes on the recordings by default.

**Horns:** "Horn [French]" and "French Horn" become the instrument French horn, "Flugel Horn" (also Flügelhorn) becomes flugelhorn – both without role credit (rules W004, W005). In general, a Discogs spelling that differs from the MusicBrainz instrument only in spaces or hyphens is no role credit (S017). A detail that already names the whole MusicBrainz instrument is no role credit either: "Trumpet [Pocket Trumpet]" is the instrument pocket trumpet, without credit.

**Engineers with several tasks:** "Engineer [Mix, Recording]" becomes one row per task – mix and recording, each without role credit; other details go with each ("Engineer [Mix, Recording, Assistant]" → both with "assistant"). The row says "on Discogs: …" with the role as Discogs writes it (S018).

**The kind of engineer said twice** (3.31.3, rule S047; collected item 101: "das muss natürlich einfach nur nach relationship recording engineer und nicht mit der Role Credit "Recording Engineer""): "Engineer [Recording Engineer]" is read as "Engineer [Recording]" – recording without role credit; "Engineer [Mix Engineer]" mix, "[Mastering Engineer]" mastering, "[Assistant Engineer]" engineer with "assistant", "[Sound Engineer]" sound engineer. Before, such a bracket stayed engineer with the bracket as role credit ("Recording Engineer").

**"Directed By"** is not always conducting, so nothing is assumed (R097): the row asks "please choose" with **conductor · chorus master · creative direction · miscellaneous support (task “director”)** (question Q003). Until you choose, the row has no type and is not added; the level follows the choice (conductor and chorus master on the recording, creative direction on the release). "Music Director" / "Musical Director" stay conductor (R056).

**"Alto"** alone (3.21.2) is the viola in Spanish and French but an alto saxophone or an alto voice in English: nothing is assumed (R102), the row asks **viola · alto saxophone · alto vocals** (question Q006), without a role credit.

**"Text"** alone (3.21.0, mostly from pasted texts and Bandcamp credits) is liner notes in English booklets but the lyrics in German ones, so nothing is assumed either (R100): the row asks **liner notes · lyricist** (question Q005); liner notes go on the release, lyricist moves the row to the works matrix. **"Logo"** and **"Logo by"** are design with the role credit "logo" (R101).

**"Sounds"** (3.30.6; maintainer: "bitte mit notizabfrage ob performer oder effects mit role "sounds" wie bei anderen instrumenten wie bass schon üblich") is a performer (R104), and the row asks **performer · effects (credited “sounds”)** (question Q008); unlike the questions above, the row stays performer until you choose. **Poems and poetry** (3.31.4; collected item 104, maintainer: "bitte Dichter immer zu lyricist", "ja das nachfragen kann man machen"): the poet is the lyricist of the works – "Poems By", "Poetry By", "Poem By" (also "Poetry Written By") are lyricist with the word in lower case as role credit ("poems", "poetry", "poem"; R105; before, "Poetry By" and "Poem By" were writer, "Poems By" an unknown instrument). Poems read out are spoken vocals on the recordings: "Poetry [Read By]", "Poems [Recited By]", "Poems Read By", "Poetry Reading", "Recitation", "Recited By" (R106), credited "poetry", "poems" or "recitation". **"Poems"**, **"Poetry"** or **"Poem"** alone asks like "Text" (R107): **lyricist (the words of the works) · liner notes (poems in the booklet) · spoken vocals (read out)** (question Q009), each with the word in lower case as role credit; until you choose, the row is not added. "Author", "Story By", "Script By" stay writer (R005). The same in pasted texts ("Poems: Jane Doe", "Poetry by John Roe") and Bandcamp credits. **From 3.32.7 the type follows the level** (collected item 104b; maintainer: "kannst du bei all den poetry credits auch es ermöglichen durchzuschalten? also works (lyrics) -> recording (vocals) -> release (auswahl lyrics/vocals)?", "ja liner notes ist auch eine möglichkeit"): a row of poems (R105, R106, R107) has every level and stays in its entry also on the works level; on the **works** it is lyricist, on the **recordings** vocal with spoken vocals, on the **release** it asks **lyricist (the words) · spoken vocals (read out) · liner notes (poems in the booklet)** (question Q010; the answer is kept for the next time the row comes to the release). Its role credit stays. A click on the level in the compact line goes **works → recordings → release → skip** and back to the works. "Poems" alone asks Q009 first, as before; once its level is switched, the level decides.

**Performers on tracks, instruments for the release** (3.31.8, rule S046, **off until switched on** in "Mapping rules"; collected item 111, maintainer, Discogs 8613662: "führt unter den tracks die performer aber die instrumente erst in den relationships. gäbe es eine möglichkeit beides zu verknüpfen? mit quick switch. standardeinstellung = aus"): some releases name the musicians of each track only as "Performer" ("Performer – Barry Guy, …" below tracks 4-3 and 4-5) and their instruments only for the whole release ("Bass – Barry Guy"). With S046 switched on, such a person's instrument and vocal rows get the tracks of the person's "Performer" credits, across all media, and the "performer" rows go – the row says "On the tracks of the “Performer” credits on Discogs: 4-3, 4-5". Someone with several instruments gets all of them on all of these tracks (Discogs does not say which where); someone without an instrument keeps "performer"; instruments without a "Performer" credit stay on all tracks; other roles (Recorded By, Design …) are not touched. Switched off again, the rows are as Discogs gives them. (From 3.32.0 also among the quick switches.)

**Basses:** Upright Bass, Contrabass and Kontrabass (also as details of "Bass", e.g. "Bass [Upright]") become double bass, with "upright bass" or "contrabass" as role credit; the German "Kontrabass" is always double bass **without** role credit – a translation, MusicBrainz's own name (3.22.3; before "Kontrabass", in 3.22.2 "contrabass"). **Violoncello** is cello with the role credit "violoncello" (3.22.2). "Bass [Electric]" and similar details go straight to the matching instrument.

**"Additional":** whether it is part of the role name ("Additional Synths", "Additional Engineering") or a detail in brackets ("Synth [Additional]"), it ticks MusicBrainz's "additional" checkbox and is not written into the role credit: "Additional Synths" becomes synthesizer with "additional", credited as "synths". The same for "Additional Musicians", "Additional Personnel" and the like, also misspelled as on Discogs ("Trombone [Additonal Musicians]" → trombone with "additional", without credit; rule S002).

**Details that repeat the role** are no role credit (S019): every word of the detail (besides "all", "by", "and", "the") is the role or the MusicBrainz type in another word form – "Mixed By [Mixing]" is mix, "Recorded By [Recording]" recording, both without credit.

**Arrangements:** if Discogs names writing credits, its arrangement credits ("Arranged By", "Orchestrated By" …) go to the works matrix too, not to the recordings.

**Levels:** each row offers only the levels where MusicBrainz has its relationship type: a producer or mix credit has no "Work" button. Deprecated types do not count, so a mastering credit offers only "Release" (and "Skip"); when one level is all there is, its buttons say so on mouse-over.

**Design:** whenever "design" appears in a Discogs role or its details, the type is design and the other words are the wording, without "design" and "by": "Cover [Cover Design]" → design "cover", "CD Designed By" → design "cd". "Graphic Design" keeps MusicBrainz's own type.

**Medium in front of a role:** "CD Produced By", "LP Mastered By" and the like describe the product, not the recording: the role goes on the release.

**Editors of texts:** "Editor [Publications Editor]" (also liner notes, magazines …) becomes miscellaneous support with the task in lower case ("publications editor"), not MusicBrainz's audio editor.

**Word forms of the role:** a Discogs role that only names the MusicBrainz role in another word form ("Produced By" for producer, "Photograph By" / "Photographed By" for photography, "Mixed By" for mix) never becomes a role credit and is not offered as one.

**A&R:** "A&R", "A & R Consultant", "A&R Coordinator" and the like become artists and repertoire on the release group; the word after "A&R" becomes its task ("A & R Consultant" → task "consultant"; plain "A&R" has none).

**Lithography** becomes design, with "lithography" (or the details in brackets) as wording for the edit note.

**Producers:** "Produced By" (also "Produced-By", "Produced", "Record Producer") is always producer, "Co-Produced By" producer with "co". Only Producer and Co-Producer go on the recordings by default; Executive, Associate, Assistant and Additional Producer go on the release. If Discogs names such a role for single tracks only, it stays on those recordings.

## Companies, etc.

Discogs lists copyright holders, studios, mastering and pressing companies in the "Companies, etc." section of a release. On Discogs all of them are "labels"; in MusicBrainz they are either **labels** (for example rights holders, distributors, pressing companies) or **places** (for example studios and mastering rooms).

**Places in the Discogs notes** (3.30.8, rule S042; maintainer: "ja tatsächlich wollen wir die orte hier angeboten bekommen. sie können ähnlich wie die publisher auch mit dem discogs feld companies entgegengecheckt werden. sofern es sich nicht um eine inhaltliche dopplung handelt können orte aus dem freitextfeld ergänzt werden."): "All music recorded … at Orange Music Sound Studios in West Orange, New Jersey" and "mastered … at Turtle Tone Studio in New York City" are added, read as in a pasted text (with their area) – unless "Companies, etc." lists the place with that role already; listed with another role, the role goes to that entry (with its Discogs link). The log names what came from the notes.

**Places looked up by name** (3.31.2, collected items 98b and 114; maintainer: "die orte kommen als vorschläge in "Companies, etc.". allerdings werden sie wohl nicht mit den places abgeglichen? … die places liegen in MB vor."): a place without a link – from the Discogs notes or a text – is looked up in MusicBrainz in the first part of its area ("West Orange, New Jersey" → West Orange, where MusicBrainz has the place); with no hit there, by its name (and other names) alone – then a place in one of the areas the source names comes first, one elsewhere is offered as "similar name" with its area. A city written at the end of the name ("Loft Köln") is found as an area by its name or other names (Köln = Cologne), and the rest of the name is looked up there ("Loft" in Cologne, similar); the entry shows "(Köln)". Only suggestions, nothing is assigned by itself; the log says "looking for the same name" (before: "no MB artist with this Discogs link").

**Rights societies** (3.31.0, rule T045; maintainer: "BMI soll auf release ebene ebene angeboten werden. evtl muss die Skriptinterne Liste aller rights societys abgeglichen werden."): the script keeps a list of the rights societies (BMI, ASCAP, SESAC, GMR, SOCAN, PRS, MCPS, IMRO, GEMA, AKM, SUISA, SACEM, SDRM, SABAM, BUMA, STEMRA, SIAE, SGAE, SPA, STIM, TONO, KODA, NCB, Teosto, STEF, ZAiKS, OSA, SOZA, Artisjus, JASRAC, KOMCA, CASH, APRA, AMCOS, SAMRO, SADAIC, ECAD, UBC, SACM, SAYCO … – shown in [Mapping rules](#mapping-rules) as T045). ## Dates

Every row has a **Date** column with the same fields as MusicBrainz's relationship dialog: **Begin date** and **End date**, each with year, month and day, plus "This relationship has ended". What you see there is exactly what goes into the editor. Rows without a date show a small **+ Date** button, so the list stays compact.

- **Paste a date as MusicBrainz shows it** into any date field, or onto the **+ Date** button: "from 2015-01-26 until 2015-01-27" fills begin date 2015-01-26 and end date 2015-01-27; "in 2015-01" fills 2015-01 as begin and end; "on 2015-01-26" fills 2015-01-26 as begin and end. "from 2015" (still ongoing), "until 2015" and "from 2015 to ????" work too, as do the German forms ("von … bis …", "am …", "im …"). A plain date such as 2015-01-26 fills only the line you paste it into. This works in the date pool form as well.
- Type a date straight into a row. Month and day can stay empty. For a single day or a year (for example ℗ 1998), enter the same begin and end date; the ⇣ button copies the begin date into the end date. As in MusicBrainz, a relationship with an end date counts as ended.
- **Begin and end one above the other:** the fields are a small grid, "Begin" above "End" – year above year, month above month, day above day.
- **A date from the pool or the matrix** is shown as a compact chip with "from the matrix" or "from the date pool" below it: **✎** opens its fields (to see or change them; **done** closes them again), **✕** removes the date.
- Below a row's open date fields: **from pool …**, **save to pool** and **✕** (remove the date). "save to pool" saves the date in the pool, named after its date group ("Performance 1" …, the name can be changed), and suggests it in the date matrix for the row's group – for the row's tracks if the row does not cover all of them – so **Apply** puts it on the other rows of the group. A date from the matrix is marked "from the matrix: …".

**Colour code** everywhere in the dashboard: dates in MusicBrainz purple, tracks in MusicBrainz orange.

### Dates & tracks

At the top of the dashboard, **Dates & tracks** holds the date pool, the track pool, the date matrix and "Find dates in free text" in one block that stays visible while you scroll (from 3.18.0 together with the line "Add entry manually" above it). A click on its title folds it to a single line with the counts ("2 dates · 2 track groups · 2 in the matrix"); it is open by default when there are dates (in the pool or in the Discogs notes), and your choice is remembered. **From 3.32.1** (collected item 109; maintainer: "automatisch dashboard aufklappen sofern daten/tracks gefunden wurden die noch auf apply gesetzt werden müssen", "das dashboard muss doch auf sein, damit Dates & Tracks sichtbar ist?"): when an import leaves suggestions in the date matrix that wait for **Apply**, the dashboard opens (if it is closed) and "Dates & tracks" opens with both pools – for this import only; what you chose stays remembered and counts again from the next import without such suggestions (folding by hand closes them again at once). **From 3.32.8** the message "n dates from the notes were placed in the date matrix …" has the button **To the date matrix** (collected item 109b): it opens "Dates & tracks" (also when folded by hand – your choice stays remembered), brings the matrix into view and lights it up briefly. Opened, its body scrolls on its own, and **▲ fold** at its bottom folds it again without scrolling back up. With **keep the pools in the bar when folded** (next to it, on by default) the dates and the track groups stay in the folded bar, so you can drag them onto rows while you scroll through the dashboard. A small "⠿ drag" next to the date pool and the track pool reminds you that their chips can be dragged. **▾ Date pool** and **▾ Track pool** (3.30.3; maintainer: "bitte mach "Date pool" und "track pool" in der mitscrollenden leiste oben auf und zuklappbar. bei großen releases kann das sonst zu viel platz wegnehmen") fold each pool on its own – in the open block and in the folded bar –, folded only its name and the number of its chips stay ("▸ Date pool (12)"); remembered (`dci-pool-fold`).

- **Date pool:** save dates there once (**+ New date**, or **save to pool** in a row where you typed one), optionally with a name such as "Session 1". Each entry shows how many rows use it; a click on it edits or deletes it. **All dates in the Discogs notes** are put into the pool by the script (see "Suggestions" below). The pool suggests ℗/© years it finds in the Discogs notes; a click puts "℗/© 1" into the ℗/© column of the matrix.
- **Join two dates into a period:** drag a pool date onto another one: a new pool date from the earlier begin to the later end appears ("Performance 1" + "Performance 2" → "Performance 1–2"; other names are joined with "+"); both dates stay. Drag the next one onto the new date to widen it further. In the matrix the same works on a date there: it then stands for the period (a date dragged from another place of the matrix goes into it, with its track groups). Begin and end can always be changed by hand with a click on the date.
- **Track pool:** named groups of tracks ("Tracks 1–5", "Overdubs"), from the dates in the text or made by hand, see below.
- **Reuse a track group:**
  - drag it onto a date in the **date matrix** (below): that date then applies only to these tracks;
  - drag it onto the **works matrix** – a column head, one of its roles, or an attribute in the head of the first column (see "Works matrix");
  - drag it onto **Tracks and status** of a row (or onto its open track list): the row gets exactly these tracks; **hold Shift** while you drop to add them to the tracks the row already has. A row on the level "Release" moves to "Recording" (a message says so). While you drag, the places it can go onto are outlined and say "drop: replace · ⇧ Shift: add"; the place under the pointer says what the drop will do;
  - in the open track list of a row, click the button of the group.
- **Reuse a pool date:**
  - drag it into the **date matrix** (below) – for whole date groups and tracks;
  - drag it onto the **date field of a row** (also of a planned link between recording and work, or a column date or cell of the works matrix): the row gets it, replacing a date it had; while you drag, the fields it can go onto are outlined, and the list scrolls when you move to its edge – as browsers do it, only after the pointer stayed in the edge zone (its lower edge, or just below "Dates & tracks") for 0.2 s, starting anew when it leaves the zone, and then the faster the nearer it is to the edge, starting gently; so dragging a chip out of the block does not make the list jump up;
  - in a row, pick it from **from pool …**.
- **clear all dates** and **clear all track groups** empty the pool of this release after a confirmation, which also offers to clear the stored pools of all other releases. Rows keep the dates they already have, as their own dates (the matrix no longer changes them). When the track groups go, the dates in the matrix would apply to all tracks: they become dashed suggestions again. The next time the release is opened, the Discogs notes are read again, so the dates and track groups from the notes are back as at the first import.
- **↻ load again from Discogs** makes the dates and track groups from the Discogs notes anew right away, as at the first import (also after the browser's storage was emptied or changed); those you made by hand stay, unless you tick "also remove the dates and track groups made by hand". Rows keep their dates until "Apply".
- Values are copied into the rows, so every row stays editable on its own. If you change a pool entry later, the dashboard asks whether to update the rows that use it.
- Pools and matrix are kept per release in this browser while the release is remembered (from 3.36.0 only with ⚙ Settings → Cache → Remember changes and import settings per release; see [Remember per release](#remember-per-release-cache)), so they are there again when you come back. If none of the dates from the Discogs notes is left in the pool (cleared, or the storage emptied), the notes are read again when the release is opened.

Relationship types without dates in MusicBrainz show "this type has no dates". Invalid dates (for example 1998-02-30, or an end before the begin) are marked in the row, and the row is not added until they are fixed.

**Check after staging:** the script reads the staged relationships back from MB's relationship editor and compares their dates with the dashboard. The log reports when all dates arrived; if a date is missing or different in the editor, the dashboard shows which relationships are affected.

### Date matrix

The matrix has one column per **date group** (Performance, Mix, Remastering, Mastering, ℗/©, see the table below); each column head shows how many rows belong to the group.

1. **Dates first:** drag a date from the date pool into a column. A date can be in several columns, but only once per column.
2. **Then the tracks:** drag a track group from the track pool onto a date in the matrix. Several track groups on one date count together. **A date without a track group applies to all tracks.**
3. **Apply** below the matrix puts the dates onto the rows of their groups:
   - Per track, the dates of all matrix entries that cover it count. Tracks with the same dates stay in one row; the others get a row of their own (the row is split, with the same instrument and credits; a message names the split rows).
   - A track covered by two dates gets one row per date, so MusicBrainz gets one relationship per date (a period would include the days in between).
   - Rows on release level take the dates marked **Release level**, and when the column has none, the dates without track group.
   - **Release level** (a checkbox on every date of the matrix, next to its track groups): this date is only for rows on the release level (release, release group); rows on recordings and works leave it out. Example: in "Performance" the studio days in March and a release concert in June; June marked "Release level" – the instrument rows on recordings get March, a row on the release level gets June.
   - **Switching the level:** a row whose date came from the matrix and that you switch to the release level gets the date marked "Release level" of its column at once; switched back to recordings, the dates of its tracks again (the log says so).
   - **Mastering and Remastering** are always on the release level, as MusicBrainz has them (on recordings the type is deprecated): these two columns have no "Release level" checkbox, every date in them goes to the mastering rows. A track group on such a date only says which mastering row takes it – "CD 1" on May for the engineer of CD 1, "CD 2" on June for the engineer of CD 2; a date without a group goes to every mastering row. The column ℗/© keeps the checkbox. A date you entered yourself stays.
   - A date that names studios (rule S016) goes onto those studios only, limited to its tracks; other studios are left alone by it. Rows of people are not affected by the studio choice.
   - Dates you typed into a row, picked there from the pool or dragged onto it stay as they are; a message names the rows that kept a date of their own.
   - **Applying again** after a change starts from the rows as they were before the previous run (copies made by the matrix go back into their row, unless you changed them), so the rows always show what the matrix says now. A date taken out of the matrix leaves its rows when you apply again.
4. **apply automatically** next to Apply (off by default, remembered): every change in the matrix goes onto the rows at once. Switched off, "not applied yet" in the head of "Dates & tracks" and below the matrix shows that the rows do not show the matrix yet.

**Suggestions (yellow, dashed):** dates in the Discogs notes with a word naming their group ("recorded", "mixed", "mastered", "℗" …) are put into the pool and the matrix by the script, with the track group and the studios of their sentence – once per release. They stay suggestions until they are applied or confirmed; a message says how many there are. The same look marks suggestions everywhere – in the works matrix, "li?", and in the pools the dates and track groups from the Discogs notes that you have not used yet (dropped onto a row, the matrix or a date, or placed by hand); the coloured left edge stays (dates purple, roles blue). Dashed outlines while dragging only show where a drop can go. Dates without such a word go only into the pool (a message says so), to be dragged into the matrix or onto a row where they belong. Separate days ("June 16 & 19") come as one entry to **choose** from: the days as on Discogs or the period (see [Track pool and dates for some tracks](#track-pool-and-dates-for-some-tracks)).

**Change an entry:** click a date in the matrix for a small editor – its column (moves it), its track groups (tick several), its studios ("only for these studios"), **✓ Confirm** for a suggestion, **edit date** (the pool entry) and **remove**. × on a date takes it out of the column, × on a track group takes it off the date. Dates and track groups can also be dragged from one column or date to another.

**Without a mouse:** every chip in the pools has a grip ⠿. Click it (or press Enter on it), then **+ place here** in a column (dates) or **+ tracks here** on a date (track groups). Esc cancels.

### Date groups

Some dates belong together: the musicians of a session and the studio where it was recorded, the mix and the mixing studio. The columns of the matrix are these groups:

| Group | Pool name | Roles | Places |
| --- | --- | --- | --- |
| Performance | Performance 1, 2 … | performer, instrument, vocal, performing orchestra, conductor, chorus master, concertmaster, recording (the recording engineer) | recorded at |
| Mix | Mix 1, 2 … | mix | mixed at |
| Mastering | Mastering 1, 2 … | mastering without "re" | mastered at (from Discogs "Mastered At" or by hand) |
| Remastering | Remastering 1, 2 … | mastering with "re" | mastered at from Discogs "Remastered At" |
| ℗/© | ℗/© 1, 2 … | phonographic copyright and copyright, labels and artists, release and recordings | – |

Nothing is copied automatically while you type, paste, pick from the pool or drag a date onto a row, so you can fill in begin and end date first. Dates you entered yourself are never overwritten by the matrix. A row added by hand gets the date its group currently uses as soon as it has its role.

### Dates in free text

**Find dates in free text** (small, folded, at the end of "Dates & tracks") takes any pasted text (liner notes, a Discogs paragraph …) and lists its dates in MusicBrainz form; the Discogs notes are always searched as well. Each date has buttons for the date groups (Performance, Mix, Remastering, Mastering, ℗/©) and "pool only": a group button saves the date in the pool ("Performance 2" …) and puts it into that column of the matrix with its track group and studios (a suggestion of the same date in another column moves there); **Apply** – or "apply automatically" – puts it on the rows. A keyword near the date ("recorded", "mixed", "mastered", "℗" …) highlights the likely group; "in the matrix: Performance" shows where a date already is. Keywords count as whole words only (the label "Fuzzoramarecords" says nothing about recording), capitalised words after ℗ or © in the same sentence belong to a name, and "©©", as Discogs sometimes writes it, makes a copyright date: "©© Fuzzoramarecords 2005" → ℗/© 2005 (rule D015).

Recognised (date rules D001 … in "Mapping rules"): ISO and MusicBrainz dates and periods, numbers with dots (day first), numbers with slashes, month names and abbreviations in English, German, Spanish and French ("November 1, 2022", "1. November 2022", "1st of November 2022", "1 de noviembre de 2022"), ordinal words ("first of November 2022"), days within a month ("March 1–3, 1998"), periods across months or years ("March 1 to April 2, 1998", "December 2003 to January 2004", "between 1997 and 1998", "1997/98"), month and year (also as numbers: "3/1996", "03.1996"), several days ("June 23 and 24, 2025", "23 and 27 June 2025"; from 3.28.5 also in numbers: "19 & 20. 01. 2009", "19./20.01.2009"), year, month name and day ("1973 October 19", 3.28.5), the year before the month (3.34.18, D024: "2024 March", "2024 January - July", "2024 Jan – Jul" → 2024-01 – 2024-07, "2024 March 3–5", "2024 March 30 – April 2"; "© 2019 March Records" keeps the year only – a name in capitals follows; such a date right after the area of a place no longer takes the area with it: "Studio Sol, Marseille 2023 March"), seasons (the year) and a year alone; "Rec." counts as "recorded". From 3.28.5: the word naming the group is looked for in the date's own sentence only ("Mixed May 2001. Released 2003." – 2003 is no mix date; a line ending in ":" belongs to the next one, D019); words joined by "and", "&" or commas give the date to each of their groups ("Mixed and mastered … in March 2026" → Mix and Mastering, D020); a year of a release or issue ("originally issued on LP in 1974", "Released 2003") is no date of the credits and is left out (D018). Decades ("late 1970s") are left out. For slash dates like 11/1/2022 a number over 12 decides; otherwise the Discogs release country decides (US: month/day, elsewhere day/month), a note says so, and the other reading is one click away.

### Track pool and dates for some tracks

Liner notes often give dates for some tracks only, e.g. "Tracks 1 to 5 recorded June 25, 2025 at Brooklyn Recording" and "Tracks 6 to 10 recorded June 23 and 24, 2025 at Scholes Street Studio". **Find dates in free text** shows, for each date, the tracks and studios named in its sentence (rules S015, S016):

- **Tracks** in the sentence: "Tracks 1 to 5", "track 3", "tracks 6, 8 and 10", "1–5", "A1 to A3", "side B", from 3.28.6 also with a side alone at one end ("C1 to D": a side that is one track, "D", or all tracks of side D), "CD2, tracks 1–5", or "Disc 2" alone for the whole medium (on releases with several media). They are matched through the Discogs positions, on releases with several media through the disc number.
- Such a date comes with a **track group** in the **track pool** ("Tracks 1–5") and goes into the matrix with it – as a suggestion when it was found in the Discogs notes, or with a group button. **Apply** then puts the date only on those tracks: "Acoustic Guitar – Liberty Ellman" for the whole release becomes one row for tracks 1–5 with June 25 and one for tracks 6–10 with June 23–24, with the same instrument and credits.
- **A medium after each date** (3.30.8, rule D021; maintainer: "nur die erste disc bekommt im date/track pool ein datum und die dazu zugehörigen tracks angeboten"): "recorded … on May 27, 2016 (Disc 1), May 26, 2016 (Disc 2) and December 11 & 12, 2015 (Disc 3)" – each date takes the medium in brackets right after it ("(Disc 2)", "(CD 2)", "(LP 1)") as its track group ("Medium 2 · CD"), and all dates of the list take the group of the word before the first (Performance).
- **Studios** of "Companies, etc." named in the same sentence get exactly these tracks and this date; the other studios are left alone by that date.
- **Dates in the titles of the tracks** (3.31.7, rule D023, **off until switched on** in "Mapping rules"; collected item 110, maintainer, Bandcamp "At Iridium 2004": "wir brauchen eine option um daten von tracknamen in den datums/trackpool aufzunehmen. die Tracknummern hat man dann ja direkt. … standardeinstellung = aus"): titles such as "March 23, 2004 (Set 1)", "March 23, 2004 (Set 2)", "March 24, 2004 (Set 1)" give each date with a day to the date pool ("March 23, 2004 · 2004-03-23"), the tracks with that date to the track pool ("March 23, 2004 · 1–2") and both as a suggestion under **Performance** into the date matrix; "Apply" puts them on the rows as usual. "(Set 1)" is no part of the date. The titles of the source are read (otherwise MusicBrainz's). Switched off again, the suggestions not applied yet go. (From 3.32.0 also among the quick switches at the top of "Mapping rules".)
- **Several days:** consecutive days ("June 23 and 24, 2025") give one period (2025-06-23 – 2025-06-24); "as single dates" turns them into separate dates (the period's suggestion is replaced). From 3.31.2 also days with commas only, right before the year: "November 7, 8, 2016", "7, 8, 9 November 2016", "7., 8. November 2016" (collected item 114; before: only the year).
- **What they have in common** (rule D014): for recording dates (Performance) given as a period or as separate days within one year, the pool also gets the common month – "2001-01-20 – 2001-01-25" → "Performance 1 (month) · 2001-01" – or, across months, the common year – "2012-03-01 – 2012-09-30" → "Performance 1 (year) · 2012". Dates in different years have nothing in common; then nothing is added. **From 3.32.0 (rule D022, a quick switch, on by default; maintainer: "auf jeden fall noch die regel, dass performance dates die über mehrere tage hinweg gehen nach meinen regeln auf den kleinsten gemeinsamen nenner gekürzt werden")** this common month or year is what the script places under Performance in the matrix ("December 11 & 12, 2015" → 2015-12, "Recorded March 1–3, 2001" → 2001-03); the period and the single days stay in the pool, to be dragged there instead. Across years the period is placed as before. Switched off, the suggestions not applied yet are placed again with the period (or "choose" for single days). Before 3.32.0 these pool dates were only offered, not placed in the matrix. **▾ at such a cell** (3.32.7; collected item 118, maintainer: "gibt es eigentlich eine möglichkeit auch zwei daten also bspw. 2016-11-07, 2016-11-08 als jeweilige relationships zu führen?", "keine Einstellung nur das ▾ je Zelle") offers instead: **n single days … – one relationship per day** (the days the source gives, or each day of a period, at most 62 – each a cell of its own; the pool gets the days of a period only when they are chosen), the **period**, or the **month** / **year** kept. "Apply" then gives each row a copy per day, as "2 dates as on Discogs" does.
- **Separate days** ("Recorded June 16 & 19, 1980", "June 23 and 27, 2025"): the pool keeps the days as Discogs gives them ("Performance 1", "Performance 2") and gets the period from the first to the last day as well ("Performance 1–2", 1980-06-16 – 1980-06-19); "Find dates in free text" shows it as "also as a period". In the matrix they stand as one entry marked **Choose**: **2 dates as on Discogs** (each day a matrix entry of its own, and each row a copy per day, so MusicBrainz gets one relationship per day) or **period** (one relationship from the first to the last day, which includes the days in between), or – when they share a month or year – **month only** / **year only**. Until you choose, "Apply" leaves it out, and "1 to choose" shows in the head of "Dates & tracks". Its track groups and studios go with the choice. If the period is deleted from the pool, the single days stay in the matrix.
- **By hand:** "+ new track group" in the track pool takes a name and the tracks (grouped by medium; a click on a medium heading selects all its tracks). From 3.30.5 the field **Tracks:** next to the name (from 3.32.1 on its line, right of it – below it only in a narrow window; collected item 90b) takes them typed in, like "Media:" in the media choice – "1-4, 6", "A1–B2" (positions of the source), "2.3" (medium 2, track 3); the ticks follow, and ticks set by hand show in the field; what is no track of the chosen media is named in red and the group is not saved. On releases with several media it is a list: **choose tracks …**, a whole medium ("Medium 2 · CD") or **all media** (one group per medium; a group with exactly the same tracks is reused). In the track list of a row, the buttons of the track groups take over their tracks.
- **Dragging onto a row** a date that has track groups in the row's column of the matrix puts it only on those tracks of the row: a row for tracks 6–10 that gets "Overdub" (tracks 7–8 in the matrix) becomes one row for 7–8 with that date and one for 6, 9, 10 as before. A row without any of those tracks is left alone, with a note.

## Role credits for existing relationships

With **add role credits to existing relationships** (footer, off by default), a relationship that already exists in MusicBrainz exactly like a row (same type, same attributes) but lacks the row's role credit or "credited as" gets it added, on recording and release level. The dashboard changes it in the editor the way MusicBrainz's own dialog does, so it shows as changed (yellow) and is submitted with "Enter edit"; the preview marks such rows with ✎. Existing credits are never overwritten. A relationship that exists without any text attribute (e.g. a design credit without task) counts as the same relationship: with the option on, the task is added to it; with the option off, no second relationship is added next to it. Rows that were skipped as "already in MusicBrainz" come back when the option is switched on.

## Updating what was staged

After "Stage in the relationship editor" a confirmation appears right next to the button. You can go back to the dashboard at any time, change dates, role credits or other details, and stage again:

- Relationships the dashboard staged before are **updated in the editor** (marked ↻ in the preview), but only if they still look exactly as the dashboard left them. This includes another instrument, attribute or relationship type for the same row ("bass" → "double bass"): the staged relationship is changed, so no duplicate is left in the editor. If you changed or removed one in MusicBrainz's relationship editor yourself, the dashboard leaves it alone and says so.
- Relationships that are no longer wanted in the dashboard (row set to Skip or to another level with its buttons or the toolbar's, matrix cell switched off) are **taken out of the editor again**, and the new level's relationships are added, with MusicBrainz's own "remove" (the preview lists them). Only relationships the dashboard staged itself are taken out, and only if they still look as the dashboard left them; one you changed in the editor yourself is named for you to remove by hand.
- New rows are added as usual.

This works as long as the page is not reloaded; a reload clears both the editor and the dashboard.

## Large releases

For releases with many media or tracks:

- **Track picker:** the medium headings show format and name ("Medium 2 · CD · Nocturnes"); a click switches all tracks of that medium on or off for the row.
- **Media choice:** the question before the import (see [Media choice](#media-choice)) leaves the other media out completely.
- **Medium:** a list in the toolbar shows one medium at a time (only the media chosen for the import), each with its format and name ("Medium 2 · CD · Nocturnes (21 tracks)"); the dashboard, the works matrix and staging then cover only that medium (release-level relationships are always included). From 50 tracks on several media the dashboard starts with medium 1 by itself: stage it, submit with "Enter edit", then choose the next medium.
- **Load medium … in the editor:** MusicBrainz's relationship editor loads the tracks of large releases only when a medium is opened. If the chosen media are not loaded yet, this button opens them there one after another (from 3.21.1 with MusicBrainz's own heading of each medium, and "Load all tracks..." for a medium shown in part) and waits until their recordings are available. If MusicBrainz's page looks different and a medium cannot be found, the dashboard says so; open it there yourself.
- **At most 500 per staging** (footer, on by default) keeps each "Enter edit" reviewable. Above the stage button the dashboard says how many rounds are needed ("1,240 relationships to stage: 3 rounds of at most 500 each. Next: round 1 of 3"); progress and the confirmation show the round, and after the last one "All staged in 3 rounds". Switch it off to stage everything at once.
- **Progress:** staging shows "Staging 120 of 500 …"; the search for same-named works shows how many tracks are checked and can be stopped. It only runs for the medium shown.

## Media choice

On a release with several media the dashboard asks **before every import** which media to import (also when the dashboard opens and the Discogs release is loaded by itself):

- One button per medium (with format, name and number of tracks), **All** and **None**, and a text field that follows the buttons and the other way round: "1-4, 5, 8" (also "1 to 4"); a number that is no medium of the release is named and the import waits until it is fixed.
- **Media without a tracklist** (3.21.1): a medium MusicBrainz has without tracks (only its title – e.g. a box set whose discs were entered without their tracklists) cannot be chosen; the dialog names such media below its intro ("Without a tracklist in MusicBrainz: media 2-13 – add their tracks in the release editor first"), and so does the log. "This release has 14 media" counts them too.
- **All media of the release** (3.21.1): when MusicBrainz's web service leaves out the tracks of a medium, or the relationships of its recordings (it does so for releases with very many recordings), the dashboard reads them from MusicBrainz's relationship editor itself (its pages of tracks, 100 at a time) – so every medium is offered, and the works and existing relationships of its tracks are known. The log names the media read that way.
- **Also import relationships on the release level (release and release group)**, on by default.
- **Load the chosen media in the relationship editor in the background** (3.20.0, off at first, remembered): MusicBrainz's relationship editor shows the tracks of large releases only when a medium is opened, and relationships can be staged only on loaded media – while the dialog is open, its media cannot be opened by hand. Ticked, the chosen media that are not loaded yet (the dialog names them) are opened right after the dialog, while the source is read (3.21.1; before: once it was read): with MusicBrainz's own **Expand all mediums** when all of them are chosen, otherwise one by one with the heading of each medium; a medium MusicBrainz shows only in part ("This medium has too many tracks to load at once") gets its **Load all tracks...** clicked. The log names each one, a message says when all are there. (Until 3.21.1 the headings of MusicBrainz's editor were not found – "2 ▶ CD" has the number before the format – and nothing was opened.)
- **Works** (3.20.0): from as many tracks without a work in the chosen media as the setting says (⚙ Settings → Works, 100), the dialog already asks what the works section would ask – **Look up works** (pressed), **Not now** or **Skip works matrix** –, with about how long the lookups take; the number follows the chosen media. The works section does not ask again.
- Preselected: all media with the release level – that is the import exactly as before. **Remember this choice for this release** preselects it the next time (you are still asked); untick it to forget the choice.
- With a choice, the dashboard has only the credits of the chosen media: credits Discogs gives for tracks of other media are left out, credits without track information go onto the tracks of the chosen media, and credits on the release level (release and release group) only come along with the checkbox. Entries left without a credit are not shown. The works matrix, the dates found in the Discogs notes, the track pool (its medium list) and the track lists of the rows only cover the chosen media; the medium list in the toolbar offers only them.
- The toolbar shows what was imported ("media 2-3 without the release level") and **Choose media …**, which asks again and imports anew after a confirmation (changes in the rows are lost). **Cancel** keeps what was imported before; cancelling the first question imports nothing, and a message offers **Choose media …**.

## Stage only some relationships

**only works** next to Recording · Release · Skip under "Level for all rows" (3.30.1: a button of its own, as it is no level, underlined in the colour of works) skips everything except the work relationships of the works matrix (composers, lyricists, writers, publishers, arrangers …) – also those set to Skip before with "Skip", which come back as work relationships. ## Keyboard

- **Esc** closes the dashboard, wherever the focus is, unless a MusicBrainz dialog is open or you are typing in a field of the MusicBrainz page (then Esc belongs to MusicBrainz). While you move a chip with its grip ⠿ (or the editor of a matrix entry is open), Esc cancels that first; open **Mapping rules** (in the dashboard or as a window) are closed first (the dashboard stays open), and the media choice is cancelled.
- **Alt+Shift+D** (Mac: Option+Shift+D) opens the dashboard or sends it to the background. Ctrl+D is not used because browsers bookmark the page with it.

## Edit note

When "Write source and summary to the edit note" is checked, the script adds one block to the edit note and updates it each time you stage more relationships:

```
Source: https://www.discogs.com/release/1234
Script: MB x Vibecode: Credits Importer v3.21.4 (userscript, https://github.com/proto-beep/MBvibecode)
Done: added 27 credit relationships from Discogs (21 recording, 4 release, 2 work); linked 2 works to recordings (1 newly created); added dates to 1 existing relationship without a date.
Dates entered in the dashboard: Session 1 1998-03-02 – 1998-03-20; Mastering 1998-07; ℗/© 1998.
Not stored in MB (Discogs wording):
- Photo Guy, photography: "Cover Photo" (Discogs: Photography By [Cover Photo])
```

With Bandcamp the source is the album URL and the summary says "from Bandcamp"; with a text, "Source:" names what you entered as its origin (or "credits text pasted into the dashboard") and the summary says "from a pasted text".

With a [supplement](#supplement-with-a-second-source), "Also from:" names the second source below "Source:", and a line after "Done" says what it confirmed, what was taken over from it only and where the sources differ:

```
Source: https://www.discogs.com/release/1234
Also from: https://testband.bandcamp.com/album/testalbum
Script: MB x Vibecode: Credits Importer v3.21.4 (userscript, https://github.com/proto-beep/MBvibecode)
Done: added 29 credit relationships from Discogs (…).
1 credit also in Bandcamp; added from Bandcamp only: Guitar Guy, trumpet (tracks 2); Anna Viola, viola (all tracks).
Sources differ: Keys Guy, synthesizer – Discogs: 2, Bandcamp: 1, 2; kept Discogs.
```

Only rows with a MusicBrainz entry are counted.

The "Done" line also names dates and attributes (live, cover …) added to relationships and links that exist in MusicBrainz already. The "Dates" line lists the dates that were used, with their names from the date pool. The last part only appears when a Discogs designation has no matching MB field. Text you write yourself in the edit note is kept. The prefilled "Add artist" and "Add work" forms get a short edit note with the Discogs source and the script name as well.

## Log

The **Log** button (in the dashboard header and next to the launcher) opens a small window in the bottom left corner. It records every step as it happens: data loaded, artists matched or created, works searched, picked or created, each staged or skipped relationship, errors, and edit note updates. You can resize it, copy its content (for example for a bug report), clear it, or hide it. The log is kept for the browser tab, so it survives a page reload.

The **Dashboard** button in the log window opens the dashboard, or brings it back into view and to the front if it is already open. Since the log window stays in place while you scroll the relationship editor, you can get back to the dashboard from anywhere on the page.

**Place:** the list in the log's head puts the log next to MusicBrainz's edit note, so you see what the script did while you write the note:

- **window** (default): its own window, as described above.
- **right of edit note** / **left of edit note**: in the page beside the edit note. The edit note keeps its place (MusicBrainz keeps managing it) and gets the rest of its width (the log takes 42 %); the log is as high as the edit note (at least 140 px) and follows it when you drag the edit note higher. If there is not enough room beside it (an edit note narrower than 640 px), the log goes above it until the page is wider; the list then shows the choice in orange with a note.
- **above edit note**: in the page above the edit note, in its full width; its height can be dragged and is remembered.
- In the page the log is not moved or resized like a window; if MusicBrainz draws the edit note anew, the log follows it. Without an edit note on the page it stays a window until one appears. The choice is remembered; **↺ Reset all settings …** (⚙ Settings) sets it back to the window.


Three entries mark the milestones: **Import complete** when all Discogs credits are in the dashboard and matched, **Checks complete** when the background search for same-named works has finished, and **Staging complete** after every "Stage", with how many relationships were added, updated, changed in the editor itself and are to be removed by hand.

## Window or page

The dashboard opens as a **window** over the page by default. With **in the page** (switch next to the **Import credits …** button, or ⚙ Settings → Appearance (until 3.29.1 General); until 3.25 also **▤ In the page** in the dashboard header) it sits in the page itself, below the button and above the relationship editor, in the page's full width – but never wider than the browser window from where it starts (3.30.1; before, a page of MusicBrainz wider than the window, e.g. with a wide relationship editor, made the dashboard as wide as that page):

- The page scrolls as usual; the line "Add entry manually" and the head of "Dates & tracks" stay at the top of the window and the footer with "Stage in the relationship editor" at the bottom, both a little more compact than in the window.
- Close hides it, the button shows it again; Alt+Shift+D works as before. Rows you jump to (from Discogs, from the works matrix) are scrolled into view below the dates block.
- **window** next to the **Import credits …** button or in ⚙ Settings → Appearance switches back (until 3.25 also **⧉ As window** in the dashboard header). The choice is remembered; **↺ Reset all settings …** (⚙ Settings) sets it back to the window.

## Windows and text size

The dashboard (as a window) and the log are windows you can place anywhere in the browser window:

- **Move** a window by dragging its title bar. It can be pushed partly off the screen, but its title bar always stays reachable.
- **Resize** it with the grip in the lower right corner.
- Position and size are remembered. When you open the dashboard again or the browser window gets smaller, both windows are moved fully into view. The ⤢ button in the dashboard header puts both back to their default place; **↺ Reset all settings …** (⚙ Settings) resets them together with all other settings (see [Settings](#settings)).
- The dashboard no longer darkens or blocks the page, so you can keep it next to the relationship editor and work in both. Escape closes the dashboard only when the focus is inside it.

**Text size:** the dashboard and the log follow the default font size of your browser, whatever MusicBrainz itself uses. The **A−** and **A+** buttons in the dashboard header change it further, from 50 % to 180 %; the setting is remembered. All spacing and field widths grow with the text. If the dashboard is too narrow for the larger text, the tables scroll sideways instead of squeezing their columns.

## Emergency reset: keep only new works

New works exist in MusicBrainz as soon as you submit their form, but their link to the recording is only staged until you click "Enter edit". If you lose track of the other changes, a new work could end up unlinked.

The script therefore remembers every work created through the dashboard (per release, in this browser) until MusicBrainz shows it linked to its recording. When you open the dashboard again and a remembered work is still unlinked, the dashboard tells you and stages its link again.

While such works exist, the footer shows an **Emergency: link only the new works** button. After a confirmation it:

1. reloads the page, which discards all unsaved changes in the relationship editor (including changes made by hand) and resets the dashboard,
2. opens the dashboard again without loading Discogs and stages only the links from the recordings to the newly created works,
3. writes a matching edit note.

Then you only need to check these links and click "Enter edit". Reloading is used because it is the only reliable way to undo staged changes in MB's editor from a script.

## Diagnosis

"Start diagnosis" in the log window records what MusicBrainz's relationship editor does while you use its own tools, for example "Batch-create new works" or "Batch-add a relationship to works": which parts of the editor's state change, works and relationships it stages, and the fields of the dialogs it opens. It only observes and changes nothing. Stop it with "Stop diagnosis", then copy the log ("Copy") and attach it to an issue, so the script can learn to use these tools.

## Inside: sources and adapters

Since 3.0.0 the script is built in two parts. Nothing changed in what you see or in what is staged, and stored settings, pools and rules stay (no reset).

- **A source adapter** reads a source and delivers a **neutral release**. There are three: **Discogs** (its API, its JSON, its URLs, numbered names "Name (2)", headings and index tracks in the track list, track specifications like "A1 to A3"), **Bandcamp** (the album page's data, the credits of the album and of the track pages) and **Text** (reads credits from lines of text; Bandcamp uses it for its credits text).
- **The mapping register** (section 2, since 3.11.0) holds every rule and word list the sources are read with; the adapters use its role notation and word lists, the core its rules (see [Mapping rules](#mapping-rules)).
- **The core** works only with the neutral release: the entries and rows, dates and the date matrix, track lists in the notes, "live", series, the forms for new artists, labels, series and works, edit notes, and the Discogs tab of the companion. A [supplement](#supplement-with-a-second-source) is a second neutral release, compared with the rows of the first; each adapter has a short mark for it (DG, BC, TXT).

The neutral release has these parts:

| Part | Content |
|---|---|
| Release | source, id and URL, title, country, notes (free text), format words ("cd", "live" …) |
| Tracks | position, title and other positions (sub-tracks), in the order of the source |
| Credits | one per person and role: **who** (the source's id, name, name as written, links), **role as written** with its parts (role and details), the name as credited, **tracks** (the whole release, a list such as "A1 to A3" with what could not be resolved, or one track) |
| Companies | who, role, catalog number, tracks (for a text: "Published by X (1, 3)") |
| Series | id, name, number, links |

A role is written in the dashboard's notation, the one Discogs uses: "Role [Detail, Detail]", several roles separated by commas. Mapping roles to MusicBrainz is the register's job (the rules in [Mapping rules](#mapping-rules)), not the adapter's. A text has no track list of its own: its track numbers are MusicBrainz's.

## Known limitations

- **Writing credits** need a work: in the works matrix, rows without a work get their roles once a work is linked or created there.
- **Publisher evidence** relies on MusicBrainz's "personal publisher" relationships between artists and labels, which exist for few publishers; without them the publisher's cells stay off until you tick them.
- **Several lyrics languages and the complete language list** were tested against a simulated MusicBrainz only. Check the first "Add work" form: if a language is missing there, choose it in the form.
- **New artists and works** are created by your own form submission. The script only prefills the forms. Web links whose type MB does not detect automatically must be assigned in the form.
- **Large releases:** the editor loads some mediums only when they are expanded. Relationships for mediums that are not loaded are skipped, and the dashboard tells you which ones. Expand the medium in the editor and apply again; relationships already added are left out.
- **Track matching** is done by order. If the track lists differ, the dashboard warns you so you can check the track selection: from 3.24.1 every import compares the number of tracks **and their titles** with the MusicBrainz release – a yellow message names what differs ("Discogs differs from the MusicBrainz release: 5 tracks instead of 4" or "2 of 4 titles differ (1: “Intro” ≠ “Song One”; …)"). Titles fit despite case, accents, punctuation, small words of several languages ("the", "of", "der", "el", "le" …), notes in brackets ("(Remastered)", "[Live]", "(feat. X)") and one letter off; different numbers never fit ("Part 1" – "Part 2"). The warning comes when the numbers differ or less than 80 % of the titles fit. A pasted text has no tracks of its own and is not compared. **Index tracks of Discogs** (a work with its parts, shown with ↳): from 3.35.1 (collected item 145; maintainer: "wahrscheinlich wird es nicht erkannt weil Discogs alle Tracks unter Werken gruppiert … kann das Dashboard alle tracks abnehmen?") their parts with positions of their own are tracks of their own – "First Encounter" with A1, A2, B1, B2 gives four tracks (before: one, so the vinyl sides of such a release did not fit), the work's credits go onto each of them, a part's credits onto its own; parts of one track ("C1a", "C1b") and an index track with a position of its own stay one track ("C1"). Positions as Discogs writes them: A1 … An or A for a whole side, then B1 …, empty sides left out, "AA", "AB". **The works as track groups** (3.35.6; collected item 145b, maintainer: "ja lass das mal anbieten, aber mit der option das auch auszuschalten. und mit der option im date track pool auf die interpretation von werken als group hier zu verzichten. an und abschaltbar jeweils holt es die daten wieder oder schließt sie aus."): each such work comes into the track pool as a track group with its name ("First Encounter" – 4 tracks), as a suggestion, to drag onto a date of the date matrix or onto a row. In the track pool **"3 works as track groups"** (ticked) leaves them out for this import: they leave the pool, and the date matrix loses them – a date only on such a work leaves the matrix; ticked again, they come back with their places ("B", like "Leave out the about text"). The next import ticks it again (maintainer: "der schalter im track pool gilt nur bis zum nächsten import"). **⚙ Settings → Dates & tracks → Offer the works of the source as track groups** (on) switches them off for every release. Rows keep the tracks they got from such a group.
- **Start from the release editor** (3.19.0) relies on the release editor's page as of October 2026 ("Enter edit" `#enter-edit`, the external links editor `#external-links-editor`, `MB.releaseEditor.submissionInProgress` and `redirectURI`); without `submissionInProgress` it falls back to the click on "Enter edit". A release editor opened by another tool that sends MusicBrainz elsewhere afterwards (seeding with `redirect_uri`) does not go on to the relationship editor; for Harmony its Release Actions have the link (3.19.1), built after Harmony's page as of October 2026.
- **Internal interfaces:** the script uses internal, undocumented functions of the MB relationship editor (`MB.relationshipEditor.dispatch`, `MB.tree`, `MB.linkedEntities`), like other well-known MB userscripts. If MusicBrainz changes them, the script needs to be updated.
- **"Already added" markers** only last until the page is reloaded. If you remove staged relationships in the editor, reload the page before importing again.
- **Emergency reset** discards all unsaved changes in the editor, not only the ones made by the script. Your browser may ask whether you want to leave the page; confirm to continue.
- **Remembered works** are stored in this browser only. Works created in another browser or before version 0.4 are not tracked.
- **Existing relationships** are detected by the related entry, type, attributes and attribute texts (such as a task or series number), not by dates or credits. For two entries of the same kind the direction is not compared.
- **Dates** are taken from what you enter. The script does not read dates from Discogs credits, because Discogs has no structured dates for them.
- **The date check after staging** looks for the relationships in MB's internal editor state. If MusicBrainz changes that structure, the log says the dates could not be checked; the dates themselves are still staged.
- **Companies** can only be matched automatically if the MB label or place has the same Discogs link. Discogs sometimes uses one "label" for both a company and its studio; check the suggested kind (label or place) before applying.
- **Bracket details** are free text on Discogs. Not all of them appear on the release as written (for example "Rhythm" or "Cover Photo"). Check the prefilled role credits before applying.
- **Works of the artists** are compared by title only (as the same-named works): a work with another title (a translated title without an alias in MusicBrainz) is not found, and of an artist with more works and recordings than the limit (4,000, ⚙ Settings → Works) only the first ones are read; works stored in the browser are read again only after the days of the setting (7), so a work added in MusicBrainz meanwhile by someone else shows up only then (or after **Clear the stored works**). Works of a group's members are found only when the members are credited themselves.
- **Similar names:** a name is compared with what MusicBrainz's search returns for its words (and, with an initial, for its written-out words); a very common last name with only an initial ("J. Smith") may bring many people – the best five are shown.
- **The "about" text of Bandcamp** is prose. The script takes only "… at Place", liner notes signed below it and (3.30.7) the members of the band ("<artist> are A, B and C") from it (and the dates); the word lists keep out private places and common phrases, but another phrase after "at" can still give an entry – as a suggestion only.
- **Areas from texts** (3.22.0) are recognized only after "recorded", "mixed", "mastered" and (3.22.2) "produced", "remixed", "engineered", and only as written with capitals; a band name with "in" in it ("Lost in Space") after "Recorded by" can be taken for a name and an area – check the area entry. MusicBrainz's search for areas is by name and alias; the region and country written after it are shown, not searched.
- **Tracks by titles** (3.22.0) need the titles in quotation marks; a title written quite differently from the track (another language, a subtitle) is "not matched".
- **Discogs rate limit:** without authentication the Discogs API allows 25 requests per minute. The script needs one request per loaded release.

## Troubleshooting

Open the browser console (F12). Messages from the script start with `[Discogs-Credits]`. If the browser blocks the Discogs API, the dashboard shows an error when loading the Discogs release. The log window (button "Log") lists every step and can be copied for a bug report. For problems with the Discogs or Bandcamp tab ("Discogs view: off"), see the [companion README](mb-vibecode-credits-importer-companion-v1.8.3-README.md).
